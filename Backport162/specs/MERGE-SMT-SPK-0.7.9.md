## 1. StageManagerToggle (SMT): does it touch anything of ours?

SMT hooks two selectors and nothing else:

| selector | process | hooked by us elsewhere? |
|---|---|---|
| `-[SBContinuousExposeModuleController setContinuousExposeEnabled:]` (ContinuousExposeModule.bundle, loaded lazily) | SpringBoard | no (grep over all sources: the class, the selector and the bundle appear nowhere else) |
| `-[DBSMultitaskingContinuousExposeController setContinuousExposeEnabled:specifier:]` (DisplayAndBrightnessSettings, loaded lazily) | Preferences app | no, and no dylib of this package is loaded into Preferences until now (`Backport162.plist` filters `com.apple.springboard`) |

So no selector is hooked twice, there is no ordering question and no `%orig` chain with anything of ours.

### The data SMT writes and who else reads it

SMT writes `SBChamoisWindowingEnabled` (domain `com.apple.springboard`) through the module controller's own `_defaults`, and in the Settings pane through the original `setPreferenceValue:specifier:`. It never writes `SBChamoisWindowingEverEnabled`.

* **`SBChamoisWindowingEnabled`**: no source of this package names the key (grep). Its consumer is the SpringBoard side that follows the default and ends in `-[SBSwitcherController setChamoisWindowingUIEnabled:]` (16.0 0x1c6178ac0 / 16.2 0x1c76006fc; `specs/group3-plumbing.md` section 3.1: the 16.0 body early-returns when the value is unchanged, otherwise sets the ivar, writes `appSwitcherDefaults setChamoisWindowingEnabled:` and calls `-[gestureManager updateForChamoisWindowingUIEnabled:]`). We hook that setter twice: `G1D.x:690` (group `G1D_Coord`: remembers the controller in a thread local so the gesture-manager hook can call `switcherControllerDidUpdateWindowManagementStyle:` in the 16.2 position) and `G3.x:781` (`g3switcher`: fails the multitasking gestures before, posts `SBSwitcherControllerWindowManagementStyleDidChangeNotification` after, which `g3topaff` and `G3B.x` (`_windowManagementStyleDidChange:`) observe). All of it is DOWNSTREAM of the default. What SMT changes is only WHO writes the default (the Control Centre tile / the Settings switch write `Enabled` directly instead of `EverEnabled` while `EverEnabled` is NO), so the stock chain is entered exactly the way it is when `EverEnabled` is already YES or when `defaults write com.apple.springboard SBChamoisWindowingEnabled -bool true` is used; those two entries into the chain are what the 16.0 code and our hooks on it were written against. HARMLESS (CODE). The setter writes the same value back into the default; the equality early return makes that a no-op, so there is no write loop.
* **`SBChamoisWindowingEverEnabled`**: no source of this package reads or writes it (grep `EverEnabled`: only `extendedDisplayEverEnabled...`, see the next point). Its only reader that matters is the 16.0 observer that presents the Stage Manager introduction, `_chamoisWindowingUIEverEnabledObserver` in `SBFluidSwitcherViewController`. `specs/group2-layout-data.md` (ivar list, line 926) records that 16.2 REMOVED that ivar, i.e. the introduction is no longer started from the switcher view controller in 16.2; keeping `EverEnabled` untouched therefore goes in the direction of 16.2, it does not fight a port. We never replace or call that observer. HARMLESS.
* **G4B education / `Group4Connect.m` "ever enabled" flag**: a different thing with a similar name. Those are the two BOOLs `extendedDisplayEverEnabledWithHardwareReqsSatisfied` / `...WithoutHardwareReqsSatisfied` of `SBExternalDisplayDefaults` (external display) and the key `SBExternalDisplayEducationReasons`; `hk_setMirroring` sets the first one for the "extended" request (`Group4Connect.m:514`), `G4B.x` reads them (`:531`) and fakes `hasShownAllExtendedDisplayEducations` (group `edu`). SMT does not touch SBExternalDisplayDefaults, and no code of ours touches the Chamois keys. No shared key. The two education flows share only the remote alert SERVICE `com.apple.SpringBoardEducation` (G4B presents its own `SBERemoteViewController` alert for the external display, `G4B.x:767`; the Stage Manager introduction is the stock one). SMT removes the second user of that service for the Stage Manager toggle, so the two can no longer be requested together by one tap. HARMLESS, if anything it removes a possible overlap.
* **G3 chamois toggles (`setChamoisWindowingUIEnabled:`) and the style-change notification**: see the first bullet. The notification is posted by OUR hook after the stock setter, i.e. only when the value actually changed, whichever code wrote the default. With SMT in place a toggle from the Control Centre while `EverEnabled` is NO now produces that notification (before: nothing happened at all, the introduction came instead), so the `g3switcher` / `g3topaff` / G3B observers run in a situation they could not be reached in before on a fresh device. That is the case they were written for (a normal toggle), not a new path. Unproven on a device (this is the first time SMT and these hooks run together).
* **Education session of the main tweak (`edu`)**: only the external-display one, see above. No interaction.
* **Windowing mode 1 / external display**: `SBChamoisWindowingEnabled` is the iPad's own Stage Manager state. The external-display side (`SBSceneHostingDisplayControllerProvider`, windowing mode 1, EDE.x) does not read it in our sources (grep). No interaction.

## 2. SpeakerPicker (SPK): does it touch anything of ours?

SPK runs only where `getprogname()` is `audiomxd` or `mediaserverd` (plist filter and the same check in the constructor). The other dylibs of the package: main `Backport162.dylib` and `Backport162SMT.dylib` filter by bundle id `com.apple.springboard` / Preferences, `AV` by `com.apple.AVKit` (apps, not the daemons), `BBD` by `backboardd`, `PTR` by `pointeruid`. None of them is injected into `audiomxd` or `mediaserverd`, and none of our sources names a MediaExperience function (grep `MediaExperience`, `audiomxd`, `mediaserverd`, `AVAudioSession`, `AVSystemController`: no hit). SPK hooks C functions of MediaExperience by address (`cmsmCopyPickableRoutesForRouteConfiguration`, `vaeRouteToSelectedPort`, `CMSUtility_IsAllowedToStartPlaying`) and swaps one data pointer (the overridability table); the AVKit hook of `AV.x` (`-[AVPlayerViewController _updateSecondScreenConnectionReadyToConnect]`, in app processes) is about the second screen of video playback, not about routes. So: no shared hook, no shared data. HARMLESS (CODE).

Indirect interaction: an extended display or HDMI/USB-C monitor with audio is what makes the speaker disappear from the picker, and our external-display work is what makes the monitor usable. SPK reacts to the audio route the daemon reports (connected `pdsp` display port), it does not read anything from SpringBoard and SpringBoard does not read anything from it.

### Interference: the launch counter and crash loops (real, small)

The counter counts every launch of `audiomxd` and of `mediaserverd` (two processes, one file) that dies within 25 s, whatever the cause, and five strikes switch the tweak off for this version. A crash loop of something else that restarts userspace (backboardd, see `BBD.x:707`: "5 consecutive short-lived launches" happened with an earlier build) restarts both audio daemons each time, which is two strikes per cycle, so about three userspace restarts within 25 s each trip SPK although the audio code is fine. The picker then silently returns to stock until `/var/tmp/SpeakerPicker.1.1.0~idle1-bp.boot` is deleted (the unified log says `crash guard: ... inactive (delete ... to re-arm)`). This is the same shape of interference as EDE's guard (EDE-MERGE-0.7.5.md section 1), with two differences: it only affects the audio picker (the stock behaviour comes back, nothing else is lost), and it was explicitly requested to keep it. It also contradicts the standing rule "no auto-disable safeguards" (OPEN-ISSUES), which is why it is listed here. The two daemons' unlink timers race on the same file (harmless, `unlink` of a missing file).

### The old standalone tools

* **AudioRouteProbe** (`com.infernowolf19.audiorouteprobe`, filter `audiomxd`, `mediaserverd`, `SpringBoard`) hooks the same function, `cmsmCopyPickableRoutesForRouteConfiguration`, with `MSHookFunction` (Probe.c:787). Two inline hooks on one function stack; with its opt-in append experiment on, both would append the speaker route to the picker list (SPK appends only what is not yet in the list, so no duplicate row, but the order of the two hooks decides which one built the entry) and both log. SPK is "the finished form" of the probe (its README). The package therefore `Conflicts` / `Replaces` `com.infernowolf19.audiorouteprobe`. Also SpringBoard-side: the probe polls `AVSystemController pickableRoutesForCategory:andMode:` there.
* **SpeakerPicker standalone** (`com.infernowolf19.speakerpicker`): same dylib, same functions: two copies would hook the same three functions twice and both would swap the policy table (`policy_set` of the second sees the first one's copy, whose entries no longer say CannotOverride, takes the `!changed` path and leaves it; the kill switch of one copy would then restore a table the other copy relies on). `Conflicts` / `Replaces`.
* **StageManagerToggle standalone** (`com.infernowolf19.stagemanagertoggle`): same two hooks; both would write the same default, so nothing would break, but the switch `smtoggle` could not turn the behaviour off. `Conflicts` / `Replaces`.
* **SwitcherDismissFix** (`com.infernowolf19.switcherdismissfix`): see section 4.

## 3. Kill switches

Convention of this package: file `<jbroot>/tmp/Backport162.off.<switch>` (a daemon can only READ <jbroot>, never write under it except `<jbroot>/var/mobile`, see BPDaemon.h; reading is all a switch needs). `Backport162.off` turns everything off. All features default ON.

| switch | file | effect | how fast | needs |
|---|---|---|---|---|
| `smtoggle` | `Backport162.off.smtoggle` (or `Backport162.off`) | both hooks call the original: the Control Centre tile and the Settings switch behave as stock again (introduction on first use while `EverEnabled` is NO) | next tap, cached for one second | nothing |
| `speaker` | `Backport162.off.speaker` (or `Backport162.off`) or the legacy `/var/tmp/SpeakerPicker.off` | the pick hook returns the daemon's list unchanged, the original overridability table is put back, the two idle-selection hooks only forward | within one second of the next audio call | nothing, with one exception: a switch that exists when the audio daemon STARTS keeps SPK from installing at all (as the original did with its off file), so removing it later needs a restart of the daemons (reboot userspace) |

Directories searched for the `Backport162.*` files by SPK: `/var/jb/tmp`, then `/tmp` (the same two the pointeruid half uses; `BBD.x` picks one of them at start). Dopamine is rootless, so `/var/jb` is the jailbreak root (SMT uses `ROOT_PATH_NS`, like `AV.x`).

Logging stays opt-in as it was: SMT has only `os_log` (two lines at install, one when its switch changes), SPK's file log is written only while `/var/tmp/SpeakerPicker.debug` or `Backport162.debug` exists. Nothing is always on.

## 4. SwitcherDismissFix: double hook? Yes, so it conflicts

SwitcherDismissFix 0.3.0 (branch `claude/switcher-dismiss-fix-ce-port`, `SwitcherDismissFix/Tweak.x`) hooks `-transitionModifierForMainTransitionEvent:` on `SBFullScreenFluidSwitcherRootSwitcherModifier` and `SBMainSwitcherRootSwitcherModifier` (Logos `%hook`, `%orig` first, acts only when the original returned nil for an animated, non-gesture switcher -> home transition), and builds, for a Stage Manager root, its own run-time class `SDFContinuousExposeToHomeSwitcherModifier` (a port of 16.2's `SBContinuousExposeToHomeSwitcherModifier`).

This package covers the same ground, more completely:
* `G1B.x:2371` (group `G1B_FluidRoot`) hooks `-[SBFullScreenFluidSwitcherRootSwitcherModifier transitionModifierForMainTransitionEvent:]` and replaces it with the 16.2 decision tree (the same selector SDF hooks, same class).
* `G1C.x:5327` hooks the same selector on `SBContinuousExposeRootSwitcherModifier` (16.2 0x1c781859c) and, for animated non-gesture 2 -> 1 and 1 -> 2 transitions where 16.0 returned nil, builds the ported wrapper (`G1C_BuildCEToHome`, class `SBContinuousExposeToHomeSwitcherModifier`, the 16.2 name; same decoded behaviour as SDF's class, `G1C.x:273` says it is derived from SDF 0.3.0).
* The class names differ (`SDFContinuousExposeToHomeSwitcherModifier` against `SBContinuousExposeToHomeSwitcherModifier`), so there is no class-name clash and nothing is "created by whichever loads first" (the old README note said so; it was wrong for the 0.3.0 name, see the README fix). But the SELECTORS are hooked twice on the same classes (`SBFullScreenFluidSwitcherRootSwitcherModifier` directly, and `SBMainSwitcherRootSwitcherModifier`, which `SBContinuousExposeRootSwitcherModifier` defers to). With both installed (load order `Backport162.dylib` before `SwitcherDismissFix.dylib`, so SDF is the OUTER hook):
  * Stage Manager root: G1C's hook returns the wrapper (non-nil) first, so SDF's `if (original) return original;` passes it through. Harmless but pointless.
  * Full-screen (non Stage Manager) fluid root, grid style: the 16.2 decision tree (G1B) returns nil for switcher -> home here, exactly as 16.2 does. SDF then sees nil and ADDS a plain `SBHomeToGridSwitcherModifier` with direction 0. That is an animation 16.2 does not have in that case; the faithful port is overridden by the old fix. Real behavioural difference, and it cannot be switched off from the package's switches (`Backport162.off.*` does not reach SDF).
  * Two hooks on every transition-modifier request in SpringBoard, each with its own logging and its own kill switch (`SwitcherDismissFix.off`).

So installing both double-hooks the same selectors and changes the result in the second case. Decision: `control` has `Conflicts` / `Replaces: com.infernowolf19.switcherdismissfix`. (`Backport162/README.md`'s note "whichever loads first creates it. Remove SwitcherDismissFix when you test this build" is replaced by this.) SwitcherTrace (branch `claude/switcher-trace`) is an observation-only trace and is not in the conflict list.

## 6. Not verified

* Nothing was run on a device. The first run of SMT together with the `g3switcher` / `g3topaff` / `G1D_Coord` hooks (a toggle from Control Centre with `EverEnabled` NO) is the unproven step; reading says it is the stock chain.

* `Backport162.off.smtoggle` lookups use `ROOT_PATH_NS` inside the Preferences app; the app has jbroot read access through the Dopamine extension like every injected process (as for `AV.x` in apps), not tested in this process.
* Whether the 16.0 Settings pane and Control Centre have other readers of `SBChamoisWindowingEverEnabled` than the switcher observer (not found in our sources; the binaries were not re-read here).
* The crash-guard interaction in section 2 and the SPK load order against AudioRouteProbe are from code reading.

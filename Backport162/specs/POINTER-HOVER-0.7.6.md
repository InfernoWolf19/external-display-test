# POINTER-HOVER-0.7.6: stuck resize arrows on the monitor and stale pixels in its last rows (iPadOS 16.0 20A8372, real 16.0 pointeruid, 16.1 / 16.2 for comparison)

Static analysis only, nothing of this was run on a device. Tags: [H] read from code, [M] inferred from code, [L] guess / not checkable statically.
Addresses: pointeruid = file vmaddr of the user's real 16.0 binary (16.0 / 16.1 / 16.2 where three are given); SpringBoard / UIKit = unslid 16.0 cache vmaddr unless marked 16.2; bbd = backboardd.
Tooling (scratchpad, not in the repo): `ptr3/fn.sh 160 '<symbol>'` (pointeruid 16.0 disassembly), `a160.sh` / `a162.sh` (cache), `ptr/bb.sh 160|162` (backboardd), class dumps `pr160/re.txt`, `UIKitCore160n.txt`, `sb160n_objc.txt`.
Builds on POINTER-CROSS-0.7.4.md (backboardd exit, installed) and POINTER-PIXELS-0.7.4.md (PTR.x). Device evidence used: daemon log lines `g4b-bbd[PID] pointerexit:` of the user's runs 13223f3a (backboardd 36338) and 6564ae3f (backboardd 37451).

## 0. Verdict

1. [H] `ptr_hidden` never installed ("PUIDDisplayContext selectors missing"): the property getters of `PUIDDisplayContext` are `objc_direct` methods (not in the method list, the callers use `bl` to plain functions: `systemPointerClient` 0x100010b90 `ldr x0,[x0,#0x40]`, `pointerRenderingController` 0x100010b00 (+0x10), `systemPointerRenderingController` 0x100010b30 (+0x20), `display` 0x100010ac4 (weak load, +0x8); 0x100010810 = `[delegate systemPointerInteractionContextForDisplayContext:self]`). Only the setters (`setSystemPointerRenderingController:` 0x100010b3c ...) are real methods. PTR.x now checks the setter and the ivars `_systemPointerWindow` (+0x28) / `_pointerRenderingController` (+0x10) and reads the ivars. The same applies to `PUIDPointerState`'s getters (`pointerAutoHidden` is read from the ivar, +0x108).
2. (A) stuck resize arrows. [H] for the mechanism in pointeruid and in the UIKit pointer arbiter, [M] for "this is what the user sees", [L] for which of the two layers (UIKit hover end, pointeruid state) actually fails on the device:
   * Hover regions are per CLIENT, not per display: `_PUIDPointerControllerClientState.activeHoverRegion` (state object per `PUIDPointerClient` in `-[PUIDPointerController _pointerClientToClientStateMap]`, ivar +0x30). SpringBoard is ONE client: UIKit keeps one process wide `+[_UIPointerArbiter sharedArbiter]` -> `_UIPointerArbiterCore_iOS` (`_activePointerRegion` +0x20, `_lastSentHoverRegion` +0x28, `_pointerClientController` +0x40) for the windows of all displays; the resize grabbers register their regions with the per-window-scene `SBSystemPointerInteractionManager` (`-[SBAbstractWindowSceneDelegate(ForWindowSceneOnly) systemPointerInteractionManager]`, caller 0x1c5f4befc; `SBFluidSwitcherSpaceUnderlayAccessoryView _updateResizeGrabber` 0x1c63ad16c registers the grabber), so the region cannot leak between displays inside SpringBoard's own region lookup (`pointerInteraction:window:regionForRequest:defaultRegion:` 0x1c5f71c98; 16.2 0x1c73e8a00 only adds the request argument to `shouldBeginPointerInteraction...` and observers).
   * `-[PUIDPointerController _movePointerToDisplay:]` (0x10000cb60 / 0x10000c9dc / 0x10000c83c) only sets `_activeDisplayContext`, calls `[old.pointerRenderingController hidePointer]`, `_restartAutohideTimer` and `_invalidateEffectSourcesPassingTest:displayContext:`. It does not touch any client state. Identical in 16.0 / 16.1 / 16.2.
   * `-[PUIDPointerController _updatePointerWithOptions:updateHandlerCollection:]` (0x10000ead4; the pointer client selection is 0x10000eb3c .. 0x10000ed2c, 0x10000ed30 .. 0x10000ef5c): with the active display's "system pointer interaction context" (`systemPointerInteractionContextForDisplayContext:`, the context id SpringBoard registers per display with `setSystemPointerInteractionContextID:display:`, pid = SpringBoard's) the FIRST client whose pid equals that context's pid and whose `activeHoverRegion` is non-nil becomes "the pointer client" (0x10000ec08 .. 0x10000ed18, no check of the hit-tested context or of the display). Else the hit-test context's client with a region whose `coordinateSpaceSourceContextID` matches; else the system client of the active display. The pointer shape (resize arrows) is the chosen client's region shape. So after a display change the SpringBoard region sent while the pointer was on the old display is applied to the new display.
   * The only pointeruid-side expiry is the automatic exit: hit state of the pointer against the region's `hitTestBounds` (empty/null -> `contentBounds`) transformed with `clientState.transformFromClientContextToDisplay` and the ACTIVE display's rendering controller `transformToLocalWindowForCoordinateSpaceTransformToDisplay:` (0x10000f0a0 .. 0x10000f168): 1 = inside, 2 = outside (chosen client == active display's system client counts as 1). Timer `startAutomaticRegionExitTimerWithDelayInterval:` (0x10000f210, interval `automaticRegionExitDelayInterval` = 0.2 s, literal 0x10002e7b0) is armed only on a 1 -> 2 change (0x10000f188 .. 0x10000f210); the handler (block 0x10000fde8, skipped when `_latchingState == 1`) clears the region and updates the pointer. After a display change the hit state is measured in the wrong coordinate space (region of the old display, transform of the new one) and the previous state is the one from the old display, so the 1 -> 2 edge is not guaranteed [M]; the user sees the arrows stay.
   * UIKit side: the region leaves the arbiter only through `-exitRegion:removeStyle:completion:` (0x189798fd0, block 0x189799108: if the region is still `activePointerRegion` -> `_setActiveHoverRegion:nil ...` 0x1897991e0 -> `PSPointerClientController setActiveHoverRegion:nil`), called by `-[_UIPointerInteractionHoverDriver _updateHover:forced:]` (0x1897b6848) when the hover gesture ends (state 3 / 4) or the arbiter state is 3 (scrolling; arbiter state from the client interaction state: 0 hidden, 1 normal, 2 fast: 0x1890bf5ec). pointeruid's own `setClientInteractionState:` (0x10000f910) is 0 only while the pointer is autohidden (0x10000f240) and 2 on high velocity (threshold literal 0x10002e800 = 100000, practically never): a display change does not tell SpringBoard anything through this channel.
   * backboardd (installed): on every display change the stock 16.0 code already sends pointerState 3 (exit) to the HIT-TEST contexts of the old display (old set minus new set, bbd 0x100050da8 .. 0x100051668, independent of the display) and the port adds the same exit for the global routes. The events are built by `_locked_eventAtTimestamp:eventContext:` (bbd 0x100053380): a plain kIOHIDEventTypePointer (0x11) event with X/Y, no digitizer child. UIKit turns pointer-only events with `BKSHIDEventPointerAttributes.pointerState` into hover input kinds in `-[_UIHIDTransformer _inputEventsForHIDEvent:contextId:]` (0x189b9cb68: kind 3 button pressed, 2 = pointerState 3, 1 otherwise) feeding a per context state machine; the hover touch phase 7 (exit) that ends `UIHoverGestureRecognizer`s is produced from a digitizer child with Range 0 (block at 0x189ba3e50) [M]. Whether that chain really ends the hover of a SpringBoard system gesture window for a GLOBAL route exit with the appended subevents (mask 0x8f4 = digitizer, button, translation, ...) was not provable statically [L]: if the appended digitizer child still says "in range", the hover does not end.
   * Which global-route pid is SpringBoard: the three routes of each display are pointeruid (skipped by the port), SpringBoard and a third client; run dd40fa0e shows `clone mirror mode request ... from pid:37419` (SpringBoard's SBExternalDisplayService) and 37419 is the lowest of the three pids (37419 / 37538 pointeruid / 37632; in run 13223f3a 36306 / 36429 pointeruid / 36495). So SpringBoard is the lowest-pid route (36306), and the exit lines `post exit ... pid 36306` DO go to SpringBoard's system gesture window route of the display left. [M] (the SpringBoard pid is now logged by G2G: `g2g: SpringBoard pid N`.)
   * 16.0 -> 16.2 differences in these paths: pointeruid hover code identical (compared in POINTER-PIXELS 0.7.4 section 2); PointerUIServices / PointerUISystemServices identical; backboardd exit for global routes (ported); SBSystemPointerInteractionManager: observer list + `pointerDidMoveToFromWindowScene:toWindowScene:`, `shouldBeginPointerInteractionRequest:atLocation:forView:` (request instead of location only), per window scene registration unchanged; UIKit: `UIHoverEvent _cancelAllGestureRecognizersAndRemoveAllHoverTouchesForWindow:` removed and `_resetHasOutstandingUpdateTouches` added in 16.2, not decoded [L]. Nothing found that makes 16.2 end the SpringBoard hover differently on its own, so the arrows may also stick on stock 16.2 [L]; the fix below is deliberate either way.
3. (B) stale pixels in the last rows: [L] no cause provable statically (as in POINTER-PIXELS). The video shows junk only after the pointer has faded and only where the circle was clipped. What the code does at that moment [H]: `_movePointerToDisplay:` -> `hidePointer` (0x100023ab8) = `setPointerState:options:3` with `pointerAutoHidden` YES, options 3 = animated (the controller itself passes 0 for the first, non animated, state: 0x10000f978 `options = hasSetupPointerState ? 3 : 0`), i.e. the blur radius / scale / intensity springs (`visibleToHiddenPointerBlurRadius` ...) run while backboardd keeps the pointer clamped on the edge, half outside; every layer of the pointer is a CABackdropLayer (child backdrop views of the shape view, shape morphing backdrop, specular copy, portal sources); nothing ever disables them again after the fade (hidden state = alpha / scale values only; `PUIDSystemPointerRootViewController`'s 19x19 luma view is paused, the rendering VC's backdrops are not). A blurred backdrop whose sampling area straddles the display edge while its radius animates is the classic source of garbage in the edge rows [L]. `CABackdropLayer` has `enabled`, `ignoresScreenClip`, `captureOnly`, `allowsInPlaceFiltering`, `marginWidth` (QuartzCore 0x1883f24c4 setEnabled:), so the layers can be switched off.

## 1. Fixes (all switchable, default ON, deliberate deviations: no shipped build does any of them)

PTR.x (pointeruid):
* `ptr_hidden` repaired (ivars instead of the direct getters).
* `ptr_hover`: hook `-[PUIDPointerController _movePointerToDisplay:]`; if the active display context changed, for every client state in `_pointerClientToClientStateMap` that is not a `_PUIDPointerControllerSystemClientState` and has an `activeHoverRegion`: `invalidateAutomaticRegionExitTimer`, `setActiveHoverRegion:nil`, `setPreviousPointerEventActiveHoverRegionHitTestState:0`. Not done while a button is held (`_isFingerDown` +0x118: drag across the edge). The `_updatePointerWithOptions:` that `pointerEventStreamProvider:didReceivePointerEvent:` runs right after (0x100008d54) then picks the new display's system client. Not cleared: system client states (the display's own portal region).
* `ptr_edge`: (1) `-[PUIDPointerRenderingRootViewController hidePointer]` while `_movePointerToDisplay:` runs (= the display that was left) hides with options 0 (no springs at the edge); (2) after that hide, and 0.7 s after any animated autohide, every `CABackdropLayer` below the rendering controller's view gets `setEnabled:NO`; `setPointerState:options:...` re-enables them (associated flag) before the next visible state.
SpringBoard (G2G.x, `g2g_hoverexit`): observer on the multi display user interaction coordinator (Group4Focus.x, `addPointerInteractionObserver:`, `pointerDidMoveToFromWindowScene:toWindowScene:`); if `_UIPointerArbiterCore_iOS activePointerRegion` has a `referenceView` (else `_coordinateSpaceSourceViewForRegion:withStyle:`) in a window of the window scene the pointer left, `-[_UIPointerArbiter exitRegion:removeStyle:completion:]` is called (async on main). This also makes SpringBoard forget the region, so when the pointer comes back to the same grabber UIKit sends it again (without it pointeruid would show a plain pointer there until the next enter). A second exit from UIKit is harmless (block 0x189799108).
backboardd: nothing more needed or changed.

## 2. Diagnostics (Backport162.debug; pointeruid lines arrive in Backport162.log as `daemon: ... ptr[PID]`)

pointeruid, per display change: `hover: pointer display A -> B: N client state(s), fix ON`, one line per client (pid, class of client state, shape, `coordinateSpaceSourceContextID`, hit state, region text), `hover: cleared N active hover region(s)`; then up to 12 `hover: update after the display change: pointer client pid .. hover region .. autohidden .. active display ..` lines in the next 1.5 s; every hover region sent by a client (`hover: client pid P sent hover region ... / NIL (hover ended)`, 20 per second). Edge: `edge-dump [left+0 | left+0.1s | left+0.4s | left+1.2s]` for the rendering controller of the display left: view hidden / alpha, then per layer (backdrops, layers that straddle the window bounds, depth <= 2): frame in display points against the window bounds (`STRADDLES-EDGE`), hidden, opacity, presentation opacity, backdrop enabled, filters; `ptr_edge: N backdrop layer(s) ... disabled / enabled`.
SpringBoard: `g2g: SpringBoard pid N`, `g2g: pointer moved from window scene .. to ..; arbiter: active region .. lastSent .. pointerState ..`, arbiter `exitRegion` / hover region sent / client interaction state traces (30 per second). Reading a recording + log: an `arbiter exitRegion` line BEFORE the `pointer moved` line means UIKit ended the hover itself (then pointeruid state was the culprit: look at the `hover:` lines); `pointer moved` followed by `exiting the hover region ... (UIKit did not)` means the exit event does not end the hover in UIKit and G2G did; `hover: client pid .. sent hover region NIL` after it shows pointeruid received the end.

## 3. Unproven / risks

* That the stuck arrows are the SpringBoard region in pointeruid (rather than something else drawing arrows) [M]; that the exit event of the port does not end the SpringBoard hover [L] (G2G makes this irrelevant if it is true).
* ptr_edge: options 0 as the "no animation" value for the rendering controller is deduced from the controller's first-state call [M]; whether junk comes from the animation, from the enabled backdrops or from the compositor is [L]. If the pointer looks wrong after hiding / re-showing, `touch /var/jb/tmp/Backport162.off.ptr_edge; killall pointeruid`. With ptr_hidden on, the portal of a hidden source must keep rendering [M, unchanged from 0.7.4].
* G2G relies on `referenceView` of the SpringBoard created UIPointerRegions (set by SBSystemPointerInteractionManager 16.2 0x1c73e8cc0 `setReferenceView:`; the 16.0 manager reads `referenceView` in willExitRegion 0x1c5f72190) [M]; regions without one are kept and logged.
* Regions of non-SpringBoard clients cleared at a display change come back with the client's next hover update (UIKit sends on state change only [M]).

## 4. 0.7.7 follow-up: user test of ed3eb1b (log db230d53, 21:40:56 .. 21:42:23, 102 display changes)

Result: the stale pixels at the monitor's last rows are gone (ptr_edge or ptr_hidden working); the pointer still jumps for a split second when leaving the iPad from a resize corner. What the log shows:
* **`_isFingerDown` is not a button.** In `-pointerEventStreamProvider:didReceivePointerEvent:` (0x100008804) `_isFingerDown` (+0x118, BOOL) = `[attributes fingerDownCount] > 0` (0x100008b54 .. 0x100008b80), i.e. trackpad fingers resting on the surface; the button state is `IOHIDEventGetIntegerValue(event, 0x110003)` (0x100008878), from which `_isButtonPressDownTransition` (+0x119) / `_isButtonPressUpTransition` (+0x11a) are derived. The 0.7.6 guard ("button held") was true at 102 of 102 display changes, so `ptr_hover` never cleared a region. Guard now: button mask of `_lastPointerEvent` > 0 (dlsym IOHIDEventGetIntegerValue; the event is already the new display's first event when `_movePointerToDisplay:` runs, 0x100008a0c before 0x100008b3c). Raw values are logged (`hover: raw state`).
* **One crossing traced completely** (iPad -> monitor, CustomPath = SBAppSwitcherPageView region, 21:41:53, pointeruid / SpringBoard / backboardd clocks agree to ms):
  53.591 SpringBoard `arbiter sends hover region CustomPath` (pointer on the iPad region) | 53.591 bbd `pointer display <main> -> 3669D08C`, exits to the global routes of the iPad (pid 43838 = SpringBoard, 44053) | 53.593 pointeruid `client pid 43838 sent hover region` | 53.598 `_movePointerToDisplay:` (`ptr_edge` hide) | 53.600 `hover: pointer display builtin -> 3669D08C`, client 43838 has an ACTIVE hover region (ctx 0x546a2b7c, hit state 1), guard "button held" -> `cleared 0` | 53.605 first update on the monitor: `pointer client pid 43838 (PUIDPointerClient) hover region CustomPath` (the first-branch selection of section 0 point 2: the iPad region is applied to the monitor, morph + position of the region) | 53.606 SpringBoard UIKit `exitRegion (active yes)` -> `sends NIL` | 53.608 `g2g: pointer moved` (active region already nil) | 53.632 pointeruid receives the NIL (27 ms after the update) -> back to the real position. Same pattern at 21:41:52.832 (RoundedRect). This is the jump; with the button guard fixed the region is cleared at 53.600, before the update at 53.605.
* **G2G never exited anything** (0 `exiting the hover region` lines): the `exitRegion` lines in the log are UIKit's own, `g2g_hoverexit` finds the arbiter's region already nil at every `pointer moved` (UIKit ends the hover itself on the hit-test exit of backboardd). Note the observer fires AFTER the sends (53.608 vs 53.591).
* **Stale enter around every display change** (most of the 102 changes, both directions): `arbiter exitRegion R (active no)` -> `sends hover region <shape of R>` -> `sends NIL`, 1..12 ms apart (e.g. 21:41:49.696 .. 49.699 RoundedRect, 49.726 .. 49.727 CustomPath; the 49.727 one reaches pointeruid at 49.728 while the active display is already the new one). Mechanism [H for the queue, M for the cause of the order]: `applyStyle:forRegion:...` (0x18979883c) and `exitRegion:...` (0x189798fd0) both run through `_performTransactionUsingBlock:` (0x18979a068) in order; the hit-test exit of the old display calls exitRegion for R while the enter of R is still queued, so `_setActiveHoverRegion:` (0x1897991e0) still sends R's shape (x2 = hover, x3 style, x4 region, x5 transaction, x6 completion) and the exit block (0x189799108) sends nil afterwards. pointeruid applies the shape if the transform completes before the nil (generation check at 0x10000b3a4): the pointer morphs towards the other display's region geometry for a frame or more. `g2g_staleenter`: exitRegion marks the region (identity), applyStyle unmarks, and a queued `_setActiveHoverRegion:` for a marked region is called with hover = nil / style = nil (the arbiter ends in the state the exit block leaves anyway; nothing is sent but a nil).
* New diagnostics: `hover: raw state: button mask, _isFingerDown byte + ivar offset / type, _isButtonPressDownTransition, _latchingState, _lockedContext`; `hover: update N ms after the display change ... | event position (x,y) shape view model (x,y) presentation (x,y) (jump D pt)` (first 20 updates in 1.5 s; D = distance between the rendered presentation position of the active display's shape view and the event position; a region snap shows as D of tens of points or more, a normal pointer as ~0 or the spring lag); `hover: client pid sent hover region ... ctx 0x.. contentBounds .. N ms after the last display change`; SpringBoard `g2g: queued enter ... shape NOT sent`.
* Unproven: that this is the only producer of the jump (a legitimately entered region of the monitor's own corner, e.g. 21:41:55.974 RoundedRect +50 ms, is kept); that the pointer button is down during the drags across the edge the guard now protects (button mask > 0 assumed from the controller's own read of 0x110003); the exact frame cost of the morph (the new `jump` numbers will show it).

## 5. 0.7.8 follow-up: coloured specks when the pointer arrives from the iPad on the monitor's bottom edge (user test of 32e50c5, log cb8a1e73, video IMG_4140)

User: the jump is gone, leaving the monitor downwards is clean (section 4 fix), but when the pointer *surfaces on the monitor from the iPad* a few glitchy pixels show.
* **Video (macro of the monitor's bottom edge, 60 fps, 1920x1080 rotated, frame by frame around 9.7 .. 10.1 s).** Frames 1..4 nothing; frame 5 a pale dot at the last row; frames 6..9 coloured fragments (red / green / white) in the last pixel rows at the pointer's x while the pointer disc fades in; frames 9..12 disc plus the specks; from frame 13 (about 0.13 s after the first dot) a clean half disc (pointer clamped on the edge). The first dot is at 9.77 s of the video = log 00:41:30.274 (`pointerexit: pointer display <main> -> 3669D08C`), so the video starts at about 00:41:20.5.
* **Log.** Every entry on the monitor shows the same: the rendering controller of the monitor had its backdrops disabled when the pointer left; the first visible `setPointerState:` of the arrival ran the old code, which re-enabled the backdrops *before* applying the state (`ptr_edge: 1 backdrop layer(s) of <PUIDPointerRenderingRootViewController 0x11280ae00; display: 3669...> enabled`, 1 ms after the display change), at which time the clamped pointer (position `{704, 1438.5}` .. `{702.5, 1439}`) has its `CABackdropLayer` (colorMatrix, 18.24 pt square) at y 1429.4 .. 1447.6 in a window of height 1440, `STRADDLES-EDGE`.
* **Fix (PTR.x, same switch `Backport162.off.ptr_edge`).** `setPointerState:options:...` applies the state first and enables the backdrops only when no visible `CABackdropLayer` of the controller's view tree is cut by the window bounds (model frames = target of the pointer's state). While the pointer stays clamped on the edge the backdrops stay off (the disc is drawn without its material, the specks cannot be produced); the first state that moves it clear of the edge enables them. Debug lines: `ptr_edge: backdrops stay disabled, cut by the display edge: <layer frame in window>` (once per arrival) and `ptr_edge: backdrops enabled, no backdrop layer is cut by the display edge any more`.
* Unproven: that the backdrop is the producer of the specks (the video shows them only in the last rows during the first 8 frames; the leaving direction was fixed with the same lever); that `setPointerState:` runs for every pointer move (otherwise the backdrops come back with the next state change, at the latest with the next hover update); the look of a pointer parked on the edge without material.
* **Result (user test of 3e333eb, logs 9a591a18 / 16b0ea5e): the user reports the specks gone.** The log shows the mechanism working: 54 `backdrops stay disabled` / 62 `backdrops enabled, no backdrop layer is cut` lines over 44 iPad -> monitor arrivals; the monitor arrivals show the layer `{{703, 1427}, {19, 19}}` (cut at y 1440) and the enable 3 .. 10 ms later, when the first pointer update moves it clear of the edge. Side effect seen in the same log: on the iPad the gate also holds while the pointer is near an iPad edge (e.g. 01:00:55.540 `{{824, 24.5}, {19, 19}}` in a 834 pt window, enabled 0.4 s later when the pointer left the edge zone), the pointer has no backdrop material for that time. Not seen as a problem by the user.

# UIKIT-APP-0.7.9: Backport162UIK, the in-app (UIKitCore) half of the 16.2 port

Dylib `Backport162UIK` (source `UIK.m`, filter `Backport162UIK.plist` = bundles `com.apple.UIKit` / `com.apple.UIKitCore`), loaded by the tweak loader into every process that links UIKit, then restricted at run time to **apps** (main executable inside `*.app/`, not `.appex`, not SpringBoard) on **build 20A8372** (`sysctl kern.osversion`). arm64 and arm64e slices (no addresses are used: plain Objective-C runtime hooks, `class_replaceMethod`, the 16.0 IMP is called for every unchanged case). Static analysis of the 16.0 and 16.2 dyld caches only; nothing ran.

Safety rules (all in the header of UIK.m): no work at load except the build / process checks and the hook installation; no ObjC messages at load; no signal handlers, threads or atexit; every hook is installed through `UIK_Hook()` which skips (and logs once, always) a hook whose class, selector or type encoding is not the one the port was written against; every hook asks its kill file at most once a second (`<jbroot>/tmp/Backport162.off`, `Backport162.off.uik`, `Backport162.off.uik_screenbounds` U1, `uik_keyboard` K1, `uik_screenlife` U2; a killed hook calls the original). Nothing can throw into the app (no `@try` needed: only ivar reads checked at install and selectors checked at install).

Log: `<jbroot>/var/mobile/Library/Caches/Backport162.uik.log` (apps may read `<jbroot>` but write only `<jbroot>/var/mobile`; first writable of `/var/jb/var/mobile/Library/Caches`, `/var/jb/var/mobile`, `/var/mobile/Library/Caches`, `/var/mobile`; rotated at 512 KiB to `.1`). Every line carries `[progname pid]`. Missing selector / class / ivar / encoding lines are written once per key without any switch; everything else needs `Backport162.debug`. Crash breadcrumb: with `Backport162.debug` the load line prints the image base of the dylib, so `Backport162UIK.dylib+offset` frames of an app crash report (ReportCrash writes one for apps) resolve against the CI build of the same commit; no handler is installed.

Items: U1 (this section), K1, U2 (later sections).

---

## U1. Screen bounds of an app window on the monitor (bug: "the window thinks it is vertical when it is horizontal after Move to display")

### What the brief assumed and what 16.2 really does
SpringBoard 16.2 writes the scene setting `screenBoundsIgnoresSceneOrientation` (`UIMutableApplicationSceneSettings setScreenBoundsIgnoresSceneOrientation:` 0x1898dd7c0 = `[[self otherSettings] setFlag:BSSettingFlagForBool(v) forSetting:0x2a]`, getter `UIApplicationSceneSettings` 0x1898dc6a0 = `[[self otherSettings] boolForSetting:0x2a]`, diff-inspector observer 0x1898de008 `_observeOtherSetting:0x2a`). **Nothing in 16.2 reads it.** Independent check done for this item: all 4.4 M instructions of the 16.2 UIKitCore `__text` were scanned for calls to the three selectors (`bl` to the `__objc_stubs` entries and direct selref loads, tables rebuilt for 20C65) with zero hits other than the definitions; the selector string exists only in UIKitCore (whole-cache string table). Setting ids 0x28 (`inLiveResize` observer, new in 16.2) and 0x2a are unused by 16.0 UIKit (ids used by the 16.0 diff inspector: 0x1-0x4, 0x6-0x8, 0xa, 0xb, 0xd, 0xf-0x14, 0x18, 0x1d, 0x20, 0x21, 0x23, 0x24, 0x26, 0x27, 0x29). So the accessor port would change nothing and is **not added**; SpringBoard's write of the setting (Y1/Y8 notes) would be dead too.

The behaviour that fixes the symptom is in `UIScreen` (found by body-diffing all 112 703 UIKitCore functions of 16.0 against 16.2, tokens: selectors, callees, immediates, branches; tools in the scratchpad `uik/`):

| method | 16.0 | 16.2 |
|---|---|---|
| `-[UIScreen _boundsForInterfaceOrientation:]` | 0x188f91da8 | 0x1890c7fc0 |
| `-[UIScreen _unjailedReferenceBoundsForInterfaceOrientation:]` | 0x18937e674 | 0x1894b4d00 |
| `-[UIScreen _mainSceneBoundsForInterfaceOrientation:]` | 0x188f91f04 | 0x1890c8150 |
| `-[UIScreen _connectScreen]` | 0x18902b55c | 0x189161788 |
| `-[UIScreen _setInterfaceOrientation:]` | 0x1890c2fe8 (body) | thunk to new `_setInterfaceOrientation:andNotify:` 0x18996a700 (same body, the two notifications only when `notify`) |

* 16.0 `_boundsForInterfaceOrientation:` (and the other two): take the rect, and if `orientation - 3 <= 1` (landscape right / left) swap width and height (origin kept) and return.
* 16.2: `if ([self _isExternal]) { if (![self _isMainLikeScreen]) swap when orientation-3 < 2 } else swap when orientation-3 <= 1`. I.e. the swap is **never done for an external screen that is main-like** (the Stage Manager extended display: SpringBoard calls `setUIKitMainLike` on it, 16.0 0x1c60612b0 / 16.2 0x1c74e0570; `_isMainLikeScreen` = `isUIKitMainLike` of the display configuration, `_isExternal` = `isExternal`). `_mainSceneBoundsForInterfaceOrientation:` also handles a nil screen like the non external branch (`cbz x20`), irrelevant for a message receiver.
* 16.2 `_connectScreen`: after `_updateUserInterfaceIdiom` and `_updateCapabilities`: `if ([self _isExternal] && [self _isMainLikeScreen]) [self _setInterfaceOrientation:1 andNotify:NO]; else [self _updateTraits];` then sets the connected flag. The UIScreen ivar `_interfaceOrientation` (+0x48) starts at 0, so the call sets portrait and, because it changed, runs `_updateTraits` and `_computeMetrics` (no notification, no periphery insets notification).

Why this is the bug: the native rect of the monitor is landscape (1920x1080). An app moved with "Move to display" gets a landscape interface orientation (3 / 4) on its scene / UIScreen (`-[_UIScreenBasedWindowScene _updateClientSettingsToInterfaceOrientation:...]`, `-[UIApplication setStatusBarOrientation:...windowScene:...]`, `_UIScenefbsSceneBasedMetricsCalculator _updateMetricsOnWindows:animated:` all end in `UIScreen _setInterfaceOrientation:`), and 16.0 then swaps the landscape rect to 1080x1920: `UIScreen.bounds`, `_mainSceneBounds`, the keyboard geometry (`UIKBScreenTraits initWithScreen:orientation:...`, `UIInputWindowController _defaultInitialViewFrame`, `+[UIKeyboard defaultFrameForInterfaceOrientation:]` all call these three methods) and the app's idea of its screen are vertical although the monitor is horizontal. Apps started on the monitor keep orientation 1 and are not swapped, which is why only Move to display shows it. 16.2 never swaps there.

### What was ported (`UIK.m`, `UIK_InstallU1`, switch `uik_screenbounds`)
* Hooks of the three bounds methods: if the orientation is 3 or 4 and the receiver is external and main-like, the 16.0 body is called with orientation 1 (16.0 swaps only for 3 / 4, so it returns the unswapped rect, exactly the 16.2 result); everything else calls the 16.0 body unchanged.
* Hook of `-_connectScreen`: the 16.0 body runs, then for an external main-like screen whose `_interfaceOrientation` ivar is not 1: store 1, `_updateTraits`, `_computeMetrics` (the 16.2 effect of `_setInterfaceOrientation:1 andNotify:NO`, no notification).
* Checked at install (and logged once if not): `UIScreen` selectors `_isExternal`, `_isMainLikeScreen`, `_updateTraits`, `_computeMetrics`, the three bounds selectors with encoding `{CGRect=...}q` (offset digits ignored), `_connectScreen` `v@:`, ivar `_interfaceOrientation` of type `q`. Receivers: all hooks and sends are on `UIScreen` instances; `_isExternal` / `_isMainLikeScreen` are in the 16.0 class dump (0x188f92f20 and 0x18982d28c, plain flag / configuration reads under the screen's unfair lock).
* Not ported on purpose: the thunk split `_setInterfaceOrientation:andNotify:` (no 16.0 caller needs `notify:NO` except `_connectScreen`, done above), the `screenBoundsIgnoresSceneOrientation` accessors (unused in 16.2, see above).

### Log lines (with `Backport162.debug`)
`hooked -[UIScreen _boundsForInterfaceOrientation:]` etc. at launch of every app; `U1 <selector>: main-like external screen 0x... , orientation N not applied to the bounds (16.2)` once per process; `U1 _connectScreen: main-like external screen 0x... put at portrait without notification (16.2)`. Always (no debug needed): `skip hook -[UIScreen ...]: ...` / `UIScreen ivar _interfaceOrientation ...` when a piece was skipped.

### Test (plain words)
Install, relaunch the app. Stage Manager on, monitor connected as extended display, open a landscape capable app (Notes, Files, Safari) in a window on the iPad, then three dots menu > Move to display. The window on the monitor must be laid out horizontally (landscape content, `UIScreen.bounds` wider than tall; the status bar and keyboard on the monitor are horizontal too). Move it back and forth, rotate the iPad while it is on the monitor: the monitor window must stay horizontal. A/B: create `/var/jb/tmp/Backport162.off.uik_screenbounds` and relaunch the app (hooks check the file once a second, so it also works live) to get the old behaviour back.

### Unproven
That `_isMainLikeScreen` is YES for the app-side UIScreen of the extended display (inferred from AV.x / 16.2 SpringBoard `setUIKitMainLike`; if it is NO the hooks never act: the debug line `U1 ...` never appears). That Move to display really reaches `_setInterfaceOrientation:` with 3 / 4 through the paths listed. Whether other causes of a vertical window remain on the SpringBoard side (scene frame / orientation settings: Z2Orient* and P1* work).

## K1. Software keyboard for text entry on the external display (bug: "the on-screen keyboard of an app on the monitor shows up wrong / rotated on the iPad")

### What 16.2 does (decoded, addresses 16.0 -> 16.2 UIKitCore)
With no hardware keyboard and a text field in a window on the monitor, **16.2 shows no software keyboard at all** (neither on the monitor nor on the iPad). The gate is `+[UIKeyboardVisualModeManager softwareKeyboardAllowedForActiveKeyboardSceneDelegate]` (new, 0x1898b5664):

```
d = [UIKeyboardSceneDelegate activeKeyboardSceneDelegate]; if (!d) return YES;
windowing = [[d visualModeManager] windowingModeEnabled];        // Stage Manager / Chamois
embedded  = [d isKeyboardOnEmbeddedScreen];
allowed   = windowing ? [UIKeyboardVisualModeManager windowingSoftwareKeyboardAllowed] : YES;   // iPad idiom
if (embedded || !allowed) return embedded && allowed;
return [UIKeyboardVisualModeManager softwareKeyboardAllowedOnExternalScreen];                  // 0x1898b5584
```
`softwareKeyboardAllowedOnExternalScreen` reads the preference `ChamoisExternalSWKeyboard` through `-[UIKeyboardPreferencesController valueForPreferenceKey:]` (dispatch_once, `boolValue`): not an os_feature flag, **nobody sets it on a retail device, so it is NO**. The 16.0 UIKit already had this decision, inline and without the external term, in `-[UIKeyboardInputMode isAllowedForTraits:]` (0x1890df490: windowing and not embedded -> input mode not allowed), `-[UIKeyboardImpl automaticMinimizationEnabled]` (0x189996608: windowing && !embedded) and `+[UIAssistantBarButtonItemProvider _isShowKeyboardButtonVisible]` (0x189cf6384: hides the show-keyboard button for an external keyboard scene). 16.2 moves it into the function above and adds it to **three places that did not have it**, which is what changes the visible behaviour:

| method | 16.0 | 16.2 | new rule |
|---|---|---|---|
| `-[UIKeyboardImpl _showKeyboardIgnoringPolicyDelegate:]` | (address not recorded; same body without the new test) | 0x189b08ce4 | after the two `shouldSuppressSoftwareKeyboard` tests: `if (!allowed) return` (the bail target is the plain epilogue): the keyboard is not shown |
| `-[UIKeyboardImpl _shouldMinimizeForHardwareKeyboard]` | 0x18909f044 | 0x1891d56b4 | `if (!allowed) return YES` (minimized) before the old body |
| `-[UIKeyboardImpl _showsScribbleIconsInAssistantView]` | 0x1899cf688 | 0x189b12918 | after `(suppressSoftwareKeyboard || floatingForced)`: `if (!allowed) return NO` |
| `+[UIAssistantBarButtonItemProvider _isShowKeyboardButtonVisible]` | 0x189cf6384 | 0x189e41c90 | `(isMinimized || delegateAsResponder._suppressSoftwareKeyboard || scribble icons) && allowed` |
| `-[UIKeyboardVisualModeManager visualMode]` | 0x189779e74 (111 insns) | 0x1898b574c (189) | mode 1 regular / 2 minimized; see below |

In 16.0 a field on the monitor therefore showed the keyboard (UIKit presented it, SpringBoard hosted its scene in the iPad's keyboard window, laid out for the monitor host: the rotated strip of DISPLAY-LEFTOVERS section 13).

`visualMode` (inputs: chamois = `windowingModeEnabled`, initialized = `[UIKeyboardImpl activeInstance]` non-nil, hw = `[[UIDevice currentDevice] _isHardwareKeyboardAvailable]`, minimized = `[activeInstance isMinimized]`, custom = `[delegate expectedInputViewSetIsCustom]`, ext = `[self textEntryFocusOnExternalDisplay]`, special = `[self expectedInputModeIsSpecialized]`, kbcam = `[[session class] activeSession] isPresented/isPresenting`): `!chamois -> 1`; `!initialized: (hw && !ext) ? ((custom||special) ? 1 : 2) : (hw ? 2 : 1)`; `initialized && !hw: (delegate.showingAccessoryViewOnly || minimized) ? 2 : 1`; `initialized && hw: (custom||special) ? (ext ? 2 : 1) : (minimized ? 2 : 1)`; kbcam presented -> 1. 16.0 had only the old terms (`hw: minimized ? 2 : 1`). New helper methods, all small: `-[UIKeyboardSceneDelegate keyboardScreen]` 0x189837eb8 (= `[[self scene] screen]`), `textEntryFocusOnExternalDisplay` 0x189839bd4 (= `![[[self scene] screen] _isEmbeddedScreen]`, YES for a nil screen), `expectedInputViewSetIsCustom` 0x189839940 (responder has an `inputViewController`, or its `inputView.frame.size.height > 0`), `expectedInputModeIsSpecialized` 0x189839ac4 (`[[[UIKeyboardInputModeController sharedInputModeController] currentInputMode] isSpecializedInputMode]`), `_windowHostingScene:didMoveFromScreen:toScreen:` 0x189839c24 (os_log + `[self forceReloadInputViews]`; invoked by `-[UIScene _noteDisplayIdentityDidChangeWithConfiguration:]` 16.0 0x1893c7d78 call site / 16.2 0x1894ff068 on every scene component that responds, so 16.0 already sends it), `-[UIKeyboardVisualModeManager textEntryFocusOnExternalDisplay]` 0x1898b5e4c and `expectedInputModeIsSpecialized` 0x1898b5f50 (forward to the delegate, NO without one).

### What was ported (`UIK.m`, `UIK_InstallK1`, switch `uik_keyboard`)
* Added to the 16.0 classes (`class_addMethod`, skipped if present): the 9 methods above plus `+softwareKeyboardAllowedOnExternalScreen` and `+softwareKeyboardAllowedForActiveKeyboardSceneDelegate` (C bodies `UIK_ExternalSWKeyboardFlag`, `UIK_SWKeyboardAllowed`, same sequence of sends as the 16.2 disassembly).
* Hooks: `_showKeyboardIgnoringPolicyDelegate:` (returns without calling the original when not allowed), `_shouldMinimizeForHardwareKeyboard` (YES when not allowed), `_showsScribbleIconsInAssistantView` (original result AND allowed), `_isShowKeyboardButtonVisible` (class method, the 16.2 expression), `visualMode` (the 16.2 table without the keyboard camera term).
* Receivers: all sends are to `UIKeyboardSceneDelegate` (class and instance), `UIKeyboardVisualModeManager` (self / class), `UIKeyboardImpl`, `UIKeyboardPreferencesController`, `UIScreen`, `UIDevice`, as in the 16.2 bodies; the sender helpers answer nil / NO for a nil receiver or an unimplemented selector. The install checks the selectors that exist in the 16.0 class dump / disassembly (list in `UIK_InstallK1`); a missing one skips the item and logs once.
* NOT ported (equivalent for flag off and Stage Manager on, or 16.2 only): `-[UIKeyboardInputMode isAllowedForTraits:]` and `-[UIKeyboardImpl automaticMinimizationEnabled]` (16.2 only differs from 16.0 for a keyboard on a non-windowing external screen, or with the flag on), the keyboard camera (`keyboardCameraNotification:`, `lastVisualMode`, the session term of `visualMode`), `UIInputWindowController` `fullScreenPresentationAssertion` / `hostAppSceneBoundsChanged` / scene coordinate conversion, `UIKBScreenTraits _activeUCBWindowForScreen:` / assistant view geometry, `UIPeripheralHost setDeactivatedKeyboard:forScene:forSuppressionAssertion:` (decoded: the 16.0 `suppressingAccessories:` method with the parameter renamed, identical body), the SpringBoard-side `_isSpringBoard` removals in `UIKeyboardSceneDelegate setKeyWindowSceneInputViews:` / `_reloadInputViewsForKeyWindowSceneResponder:` (they only matter inside SpringBoard) and the text-suggestion calls added there.

### Log lines (with `Backport162.debug`)
`K1 added +[UIKeyboardVisualModeManager softwareKeyboardAllowedOnExternalScreen]` ... and `hooked -[UIKeyboardImpl _showKeyboardIgnoringPolicyDelegate:]` ... at launch; `K1 ChamoisExternalSWKeyboard preference = 0`; per use (max 40): `K1 _showKeyboardIgnoringPolicyDelegate: returns without showing: software keyboard NOT allowed (text entry focus on the external display)`, `K1 _shouldMinimizeForHardwareKeyboard answers YES: ...`; `K1 keyboard scene delegate 0x...: window hosting scene ... moved from screen ... to screen ..., forceReloadInputViews`. Always: `skip hook ...` / `K1 skipped: ...` / `K1: ... missing ...`.

### Test (plain words)
Stage Manager on, monitor connected, an app with a text field (Notes) in a window on the monitor, **no hardware keyboard**: tapping the field must show no software keyboard on the monitor and none on the iPad (the iPad must not grow a rotated keyboard strip; with the G3B kbhosthere fix that was already hidden). With the hardware keyboard connected the field takes input and only the minimized accessory bar may appear. An app window on the iPad itself keeps its normal software keyboard. `Backport162.off.uik_keyboard` restores the 16.0 behaviour (keyboard shown). Set the preference `ChamoisExternalSWKeyboard` (UIKeyboardPreferencesController domain, YES) to get 16.2's "internal" allowed-on-external mode: not tested, not promised.

### What to relax in G3B.x `kbhosthere` (do NOT do it yet)
After K1 the keyboard scene is never presented for a host on the monitor while the flag is off, so the `kbhosthere` rule (the iPad's hosted keyboard window refuses a keyboard whose host scene is on the other display) stops being reached for software keyboards; it stays correct for the minimized accessory bar and costs nothing. Relax it (restore the literal 16.2 `updateMedusaHostedKeyboardWindowForScene:isForeground:` third branch) only after a device log shows K1 refusing the show on the monitor (`K1 _showKeyboardIgnoringPolicyDelegate: returns without showing`) and no `hosted keyboard window ... SHOWING` of the iPad window for a monitor host with `Backport162.off.kbhosthere` created as an A/B test. NEEDS EDIT IN G3B.x only at that point.

### Unproven
That the keyboard of a monitor field is shown through `_showKeyboardIgnoringPolicyDelegate:` in 16.0 (other presentation paths via `UIInputWindowController` placement were not decoded: if a keyboard still appears the next suspect is the placement code reading `visualMode` 1); that the app side `activeKeyboardSceneDelegate` is the monitor window's delegate at the time of the tap; that `UIKeyboardInputMode isSpecializedInputMode` / `UIKeyboardSceneDelegate responder` exist in 16.0 (otherwise those terms read NO and a line is logged); the hardware keyboard `visualMode` terms (custom / specialized input view) change the minimized state for custom input views on the iPad too, as in 16.2.

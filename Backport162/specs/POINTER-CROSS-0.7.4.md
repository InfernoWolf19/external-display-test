# POINTER-CROSS-0.7.4: pointer leaving the extended display, iPadOS 16.0 (20A8372) vs 16.2 (20C65)

Static analysis only (dyld caches + backboardd from the two builds + pointeruid from the 16.1 / 16.2 IPSWs (scratchpad `pu161/`, `pu162/`, diff script `ptr/pudiff.py` logic inline); tooling in scratchpad `ptr/`: `bb.sh 160|162 <addr> <n>` = annotated backboardd disassembly, `bbd160_re.txt` / `bbd162_re.txt` = class dumps with addresses).
Addresses: SpringBoard / BackBoardServices / UIKit = unslid cache vmaddr 16.0 / 16.2; "bbd" = file vmaddr of `/usr/libexec/backboardd` (16.0: `bbd/backboardd`, 16.2: extracted from the 16.2 IPSW).
Tags: [H] read from code, [M] inferred from code, [L] guess / not checkable statically.
Context: the artifact also happens with ExtendedDisplayEnabler alone, so it is stock 16.0 behaviour. Question answered here: what did Apple change in 16.2 and can we port it.

## 0. Verdict (short)

1. [H] Apple DID change the pointer routing for display-to-display transitions in 16.2, but only in **backboardd** (`BKMousePointerController`) plus the event-attribute wire format in BackBoardServices. 16.2 explicitly sends an **exit** event to the *global* event routes (contexts registered through `requestGlobalMouseEventsForDisplay:targetContextID:`) of every display the pointer is no longer on. 16.0 never does: global routes only receive "moved" events while the pointer is on their own display; nothing tells them it left.
2. [H] pointeruid (the daemon that draws the pointer, extracted from the 16.1 and 16.2 IPSWs; no 16.0 iPad IPSW exists for 20A8372) does NOT depend on that exit to remove the pointer image: on the first event of another display it runs `-[PUIDPointerController _movePointerToDisplay:]` (16.2 0x10000c83c), which calls `hidePointer` on the previous display's rendering controller. Between 16.1 and 16.2 pointeruid is identical in everything that matters here (only the pointer shape `feather` property and a 3-instruction `_transformForLayer:inContext:` wrapper are new; 519 vs 523 methods, 9 differ). PointerUIServices / PointerUISystemServices client frameworks: identical 16.0 vs 16.2. QuartzCore: no cursor/pointer delta.
3. [M] The "pointer stuck as resize arrows on the extended display until moved again" (OPEN-ISSUES, uninvestigated) IS explained by the missing exit: SpringBoard's system gesture window of each display is a global route; its UIKit pointer interaction (resize grabber region) never gets a hover end when the pointer leaves that display in 16.0, so the client's hover region stays active in pointeruid (`PUIDPointerClient activeHoverRegion`) and is shown again when the pointer returns, until the pointer moves.
4. [L] The stale pixels (pink/cyan/white fragments, dark rectangles, green specks on the cut line) are NOT explained by any 16.2 change found. The image is removed by pointeruid's `hidePointer` (state change `setPointerAutoHidden:YES`, `setPointerState:options:3`, 0x100023858) in 16.1 and 16.2 alike; the pointer sits clamped on the edge (half clipped) when that animation starts. Most likely baseline behaviour of pointeruid's portal / luma-tracking backdrop layers (`PUIDPointerShapeBackdropView`, `_PUIDPointerPortalSourceView`, `_UILumaTrackingBackdropView` in `PUIDSystemPointerRootViewController`) being animated at the display boundary, i.e. pointeruid + compositor / display pipeline: not something 16.2 fixes, not portable by SpringBoard or backboardd tweaks. Statically unprovable.
5. Portable: (a) backboardd global-route exit (fixes the stuck resize arrows / stale hover state, section 4); (b) small SpringBoard option `pinOnButtonDown` (section 4.3, drags). Neither is expected to remove the stale pixels; confidence that anything portable fixes the pixels: LOW.

## 1. Who draws / routes the pointer (both builds) [H unless marked]

* Pointer *model* (position, display, regions, edge clamping) and HID event routing: **backboardd** `BKMousePointerController` (+ `BKMousePointerRegionArrangement`, `BKMouseEventAccumulator`, `BKMousePointerServiceServer` for the BKS API). Position math, clamping (`_locked_updatePointerWithProposedGlobalPoint:...` bbd16.0 0x10005352c / 16.2 0x100054b0c) and `_locked_getUnconstrainedHitTestPoint:...` (16.0 0x10005252c / 16.2 0x100053a44, only adds a nil-region guard + log "getUnconstrainedHitTestPoint: no displayUUID") are unchanged in behaviour. No hardware cursor: no cursor/pointer string or method delta in QuartzCore (sstr diff empty), IOMobileFramebuffer strings identical (149 = 149); the visible pointer is composited from layers.
* Pointer *image / material / shape morph*: **pointeruid** (`/System/Library/PrivateFrameworks/PointerUIServices.framework/Support/pointeruid`, `com.apple.PointerUI.pointeruid`; a UIKit app: `PUIDPointerController`, per display a `PUIDDisplayContext` with a `pointerRenderingWindow` and a `systemPointerWindow`, scenes `...pointerRenderingScene` / `...systemPointerScene`). SpringBoard creates the scenes per display through `SBMousePointerManager` -> `PSPointerSystemClientController prepareScenesForPointerForDisplayConfiguration:` (PointerUISystemServices, identical in both builds) and presents them via the display's scene presentation binder (`SBSceneManager add*SceneToPresentationBinder:` / `updatePresentationBinder:`). pointeruid receives the pointer events of each display on its own event streams (`createStreamsForDisplay:context:`, `-pointerEventStreamProvider:didReceivePointerEvent:` 16.2 0x1000084e0; it reads `BKSHIDEventGetPointerAttributes`, `hitTestContexts`, fingerDownCount, pointerEdgeMask; no contextMove/contextType string in the binary) and maps the event's context id to a display (`_displayContextForPointerEventContextID:`); when the id differs from the previous event ("Got a pointer event with contextID ... moving pointer to display") it runs `_movePointerToDisplay:` 0x10000c83c: set `_activeDisplayContext`, `[oldContext.pointerRenderingController hidePointer]`, `_restartAutohideTimer`, `_invalidateEffectSourcesPassingTest:displayContext:` for the old display. `hidePointer` = 16.2 0x100023858: `state = [pointerState mutableCopy]; setPointerAutoHidden:YES; setPointerState:options:3 updateHandlerCollection:nil error:nil` (animated). 16.1 and 16.2 pointeruid are identical for all of this (method-by-method masked instruction diff). 16.0 pointeruid: not obtainable (no 16.0 iPad IPSW), assumed = 16.1 [L]. `BKMousePointerDisplayRenderer` in backboardd is only the debug visualization (`_reevaluteMousePointerVisualizationFromDefaults`); 16.2 gives it `displayController:` / reference-space layer, irrelevant for the normal pointer.
* Hover regions (resize arrows, lift, highlight) are UIKit `UIPointerInteraction` in the client (SpringBoard's per-display system gesture window, apps) -> `PSPointerClientController setActiveHoverRegion:` -> pointeruid. SpringBoard registers its gesture window of each display twice: `-[SBSystemGestureManager _configureForNewSystemGestureWindowIfNecessary]` 16.0 0x1c6319958 / 16.2 0x1c77b912c calls `BKSMousePointerService requestGlobalMouseEventsForDisplay:targetContextID:` (16.0 call 0x1c6319b88; 16.2 uses the `...options:` variant at 0x1c77b937c) and `SBMousePointerManager setSystemPointerInteractionContextID:displayWithHardwareIdentifier:` (identical, 16.0 0x1c607e724 / 16.2 0x1c7501c5c). Both `requestGlobalMouseEvents...` selectors exist in 16.0 BackBoardServices.

## 3. Consistency of the artifact with the delta

* The stuck resize arrows fit the delta (section 0.3): 16.0 backboardd gives the extended display's global routes no end-of-hover; pointeruid hides the *pointer* of the old display on the next display's first event but the SpringBoard client's hover region (`PUIDPointerClient.activeHoverRegion`, cleared only by the client or `_automaticHoverRegionExitTimer` / "Automatic Region Exit Delay") stays; when the pointer comes back, the old region (resize arrows) is applied until the pointer moves.
* The stale pixels do not fit any delta found. Order of events seen in the video (clipped circle, fragments for a few frames, dark rectangles >= 0.5 s, specks) matches pointeruid's hide path starting while the pointer is clamped on the edge, with the shape's portal / backdrop layers (luma tracking backdrop, portal source views, match-move sources: `PSMatchMoveSource shouldBeInvalidatedIfPointerLeavesDisplay`, `invalidatedPortalSourceCollections:matchMoveSources:`) animating half outside the display [L]. pointeruid's logic for that is unchanged 16.1 -> 16.2 (only `feather` added; its effect on the edge case unknown [L]).
* Not consistent with a missing SpringBoard piece: all SpringBoard pointer deltas (section 2.2) are bookkeeping or gating that is satisfied on a mode-1 extended display; client frameworks identical.
* Display pipeline: IOMobileFramebuffer 291.0.19 -> 291.2.5.1 (strings identical, 149 = 149), QuartzCore (`CADisplayMode ... rates:`, `CAWindowServerDisplay maxLayerBandwidth`, CAFlipBook raw surface) changed, none cursor/pointer related; CoreDisplay / DisplayServices are not in the cache. Not diffable here, not portable.

## 4. Faithful port for the portable part

### 4.1 Where it lives
backboardd -> `Backport162BBD/` (separate tweak, filter backboardd, 20A8372 only, never installed; needs userspace reboot). Nothing in SpringBoard can post events to another display's global route.

### 4.2 Pseudocode (backboardd, 16.2 semantics expressed through the 16.0 event API)
```
%hook BKMousePointerController                    // methods are called with self->_lock held (`_locked_` prefix, os_unfair_lock_assert_owner)
- (void)_locked_processOneAccumulatedEventAtTimestamp:(uint64)ts shouldDisableDeltaPointerLocationUpdate:(BOOL)d {   // 16.0 0x100050c34
    %orig;
    NSString *cur = [[self _pointerRegion(ivar)] displayUUID];                 // 16.0 ivar +0x60 (read by name at runtime)
    if (!cur) return;                                                           // 16.2 gate: processingInfo first word == 1
    id poster = [[BKHIDEventPoster alloc] initWithDispatcher:[config eventDispatcher]];   // as at 0x100050e68..0x100050e8c
    for (NSString *uuid in [_globalEventRoutesByDisplayID allKeys])            // ivar +0x140 in 16.0
        if (![uuid isEqual:cur]) for (route in routes[uuid]) if (BP_Within(route)) {   // `_withinContext` does not exist in 16.0: keep it in an associated object / side table
            BP_SetWithin(route, NO);
            ev = [self _locked_eventWithPointerState:<EXIT STATE> timestamp:ts eventContext:route.destination unacceleratedRelativePoint:{0,0} acceleratedRelativePoint:{0,0} poster:poster];  // 16.0 0x100052de8
            [config.hitTestObserver ... appendSubeventsForEventTypeMask:0x8f4 toTopLevelEvent:ev interfaceOrientation:orient(uuid) getEventSummary:nil];   // as 0x100054598..0x1000545dc
            if (route pinned) remove from _globalContextsPinnedByMouse (ivar +0x148) and log "unpinning global destination" }
    for (route in routes[cur]) BP_SetWithin(route, YES);                       // 16.2 `_locked_sendMousePointToGlobalContexts` sets it
}
- (void)_locked_sendExitEventsAfterTerminatingDisplayLink:(id)x { %orig; <same exit loop with only=nil, except=nil, exitPinned=NO> }   // 16.0 0x100054278
```
What is NOT known and decides whether this works on 16.0 clients: which wire value 16.0 consumers treat as "pointer left" for a *global* route. 16.0 backboardd sends pointerState 3 (`_locked_exitEventForEventContext:` 0x100052b9c) to exited hit-test contexts and 4 (with `pointerEdgeMask` and the hit-test list) to global routes as the normal move. 16.2 changed the wire format (contextType 2 = global, contextMove 2 = exit, set by `setContextType:`/`setContextMove:` in `_locked_eventAttributesWithContextType:contextMove:...` 0x100054488); its BackBoardServices maps legacy values differently (3 -> move 1/type 2, 4 -> move 2/type 0), so the legacy numbering cannot simply be carried over [L]. pointeruid 16.1/16.2 contains no contextMove/contextType string (it reads `hitTestContexts` / `fingerDownCount` / `pointerEdgeMask`), UIKit 16.0 and 16.2 neither: the consumer of the exit is therefore UIKit's hover handling in the SpringBoard gesture window, reached through `pointerState` / digitizer range flags in the IOHID event, not through new fields [M]. Using state 3 (the 16.0 exit value) for the route destination is the closest 16.0-native choice [L]; if it does not end the hover in the 16.0 UIKit, the fix cannot be done from backboardd alone. Do NOT expect it to change the pixels (section 0).

### 4.3 SpringBoard side (optional, small)
`pinOnButtonDown` for the system gesture windows: hook `-[BKSMousePointerService requestGlobalMouseEventsForDisplay:targetContextID:]` for the duration of `-[SBSystemGestureManager _configureForNewSystemGestureWindowIfNecessary]` (thread-local flag; 16.0 0x1c6319958, call 0x1c6319b88) and forward to `requestGlobalMouseEventsForDisplay:targetContextID:options:` with `[BKSMousePointerGlobalContextOptions build:^(m){ [m setPinOnButtonDown:SBFIsChamoisExternalDisplayControllerAvailable()]; }]` (16.2 block 0x1c77b9458). The 16.0 backboardd already honours it (`pinOnButtonDown` read at bbd 0x100050f28; "pinning global destination" log) [H]. Hooks that could collide: none for these selectors in Backport162 today (G1D.x hooks only `SBSystemGestureManager shouldSystemGestureReceiveTouchWithLocation:`; G4B.x hooks `BKSMousePointerService pointerSuppressionAssertionOnDisplay:...` inside lockedptr2 only as a caller, `SBMousePointerManager pointerClientController:sceneDid...` for presubset). This does not influence the pixels.

### 4.4 Process
1. First install Backport162BBD in log-only mode (section 5) to confirm the diagnosis before any behaviour change. 2. Then enable the exit post. 3. Userspace reboot after each BBD change. Kill switch `Backport162.off.pointerexit` (BP_OnName).

## 5. Device probes that settle it

1. **Is the exit really missing / does a global client ever see the pointer leave** (no backboardd tweak needed): SpringBoard `Backport162.debug`, add a log in a hook of `-[UIHoverGestureRecognizer setState:]` (or `-[_UIPointerInteractionHoverDriver ...]`) restricted to windows of the extended display's system gesture window: move the pointer off the bottom edge; expected on 16.0 = no `Ended`/`Cancelled` transition (and the resize-arrow stuck case = region still active), on a 16.2 device = Ended.
2. **backboardd log-only package** (Backport162BBD, log line prefix `g4b-bbd`): hook `_locked_processOneAccumulatedEventAtTimestamp:...` (16.0 bbd 0x100050c34) and log current display UUID + counts and UUIDs of `_globalEventRoutesByDisplayID` + `_globalContextsPinnedByMouse` at every display change. If the extended display's route list is non-empty and no event follows after the change, the diagnosis holds. The stock debug lines (os_log debug, BKLogMousePointer, "exit context:%X" bbd 0x1000d482f, "pinning/unpinning global destination") can be used instead if debug logging of backboardd can be enabled on the Dopamine device.
3. **pointeruid state**: `ps` for `pointeruid`, then `kill -STOP/-CONT` or kill pointeruid (launchd respawns it) right after the artifact: if the dark rectangles disappear only when the pointer is moved / the daemon restarts, the leftover is pointeruid layer state, not backboardd.
4. **Video / screenshot differential**: record with only the main display pointer moved off a window edge (no display change) vs the display crossing; same rectangles on a non-extended-display edge would point to the compositor, not to the crossing.
5. SpringBoard `SBLogPointer` lines exist in both builds ("preparing scenes for pointer ... display" at 16.0 0x1c607f404 path; 16.2 prints hardwareIdentifier): check that the pointer scene of the extended display is prepared exactly once and not invalidated/re-prepared when the pointer crosses (`sb_displayWindowingMode` flip would show as prepare/invalidate pairs).

## 6. Unsure list
* pointeruid 16.0 (20A8372) is not available (no 16.0 iPad IPSW; 16.1 20B82 and 16.2 20C65 pointeruid were extracted and diffed: 9 of 523 methods differ, none in display switching / hide): 16.0 is assumed to equal 16.1 [L].
* What pointeruid's `feather` (new in 16.2: `PUIDPointerShapeView setFeather:` / `presentationFeather`, `_updatePointerWithOptions:...` +11 instructions) changes visually: not decoded; it could soften the shape mask edge [L], not display-transition logic.
* Numeric meaning of legacy pointerState in 16.0 consumers [L]; contextType/contextMove values are from 16.2 call sites (type 1 hit-test, 2 global; move 0 within, 1 entered, 2 exit) [M].
* That the stale pixel content comes from pointeruid's backdrop / portal layers and not from the display pipeline: [L], no static evidence either way; IOMobileFramebuffer / CoreDisplay internals not diffable.
* `sb_displayWindowingMode` of the extended display under ExtendedDisplayEnabler (decides whether SpringBoard creates the pointer scenes at all in 16.0): not checked; the pointer is visible there, so the gate passes in practice [M].
* Unchecked: `UIHoverEvent _cancelAllGestureRecognizersAndRemoveAllHoverTouchesForWindow:` removal in UIKit 16.2 (app-side hover lifecycle) [L].

## 7. Addendum: wire value decided, implementation (Backport162BBD, group `pointerexit`)

Corrections to section 4.2 / 6 (the "[L]" legacy-mapping items), decoded from 16.2 BackBoardServices 0x18e4832a8 (setter) / 0x18e4832ec (getter) and the tables at 0x18e4c52d8 / 0x18e4c52f8 [H]:
* setter `setPointerState:s` (s = 1..4): contextType = {1,1,1,2}[s-1], contextMove = {1,0,2,0}[s-1], i.e. legacy 1 = hit-test entered, 2 = hit-test within, **3 = hit-test exit (type 1, move 2)**, **4 = global within (type 2, move 0)**. The earlier reading "3 -> (move 1, type 2), 4 -> (move 2, type 0)" was wrong.
* getter `pointerState`: type 2 (global): within 4, entered 4, **exit 3**; types 0/1: within 2, entered 1, exit 3. So a 16.2 global exit (type 2 / move 2) is what every legacy consumer reads as **pointerState 3**.
* Consumers: UIKit 16.0 and 16.2 read only that getter at 3 sites that matter (identical code in both builds): `_UIHoverTouchDeliveryTable updateForEvent:forcingHitTest:` (16.0 0x189b8f6f0 / 16.2 0x189cd5c28: `pointerState == 4` = "global event", skips the hit test of the touch's recognizers; any other value, 3 included, resolves them normally), `_UIHIDTransformer _inputEventsForHIDEvent:contextId:` (16.0 0x189b9cb68, `== 3` = ended phase), arbiter code. Hover recognizer exit itself (`_hoverExited:`) is the UITouch phase 7 set in the digitizer update block (16.0 0x189ba3e50, driven by the digitizer Range/Touch fields), not by a pointer field. No consumer reads contextType/contextMove (no such selector in UIKit 16.2). [H for the decoding, M for "this ends the SpringBoard resize hover": not provable statically]
* 16.0 wire value for the exit of a global route = **pointerState 3**, the value 16.0 backboardd itself sends for exited hit-test contexts (`_locked_exitEventForEventContext:` 0x100052b9c = tail call of `_locked_eventWithPointerState:` with 3). 16.0 never sends it to global routes (state 4 only: 0x100050fdc, 0x1000511d0, 0x1000545b8).
* 16.2 order inside `_locked_processOneAccumulatedEventAtTimestamp:` (0x100051ca0): moves to global routes of the current display (`_locked_sendMousePointToGlobalContexts`, contextMove 1 = first event after entering the display, 0 afterwards, sets `_withinContext`), pinned globals, then **only if `hitTestReason == 1`** (accumulator: 0 = gesture in progress, 1 = no button, 2 = button just went down, 3 = button held) the exit for every other display (`exitPinned = YES`), then hit-test context events. `_locked_sendExitEventsAfterTerminatingDisplayLink:` takes a display UUID (16.0 and 16.2): 16.0 sends state-4 zero-position events to the routes of that display, 16.2 sends exits (only=uuid, exitPinned=NO). The exit event is a normal global event (token = route context, position = last point of the route destination, attributes incl. edge mask / hit-test list, subevents mask 0x8f4 appended) with zero deltas.
* pointeruid (a global-route client of every display, no state filter, `-[PUIDPointerController pointerEventStreamProvider:didReceivePointerEvent:]` 16.2 0x1000084e0) calls `_movePointerToDisplay:` whenever the context of an event differs from the previous one: an exit for display A delivered after the first move for display B would pull the pointer back for a frame.

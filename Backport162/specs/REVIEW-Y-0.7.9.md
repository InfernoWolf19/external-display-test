# REVIEW-Y-0.7.9 - differential review of the Y1 .. Y16 hooks against the 16.0 (20A8372) and 16.2 (20C65) disassembly

Method: every hook body was compared with the decoded 16.2 method (pseudo decompiler diff 16.0 -> 16.2 and the raw instruction stream where the CFG mattered), the receivers and selectors were checked against the 16.0 class dump (selector present on the receiver class or a superclass; a selector that only exists at run time is named), argument and return types against the AAPCS64 layout seen in the 16.2 code (HFA CGRect / CGSize, BOOL vs long long, out parameters), ARC ownership against the callers, and scopes (thread local overrides) for early returns.
Not reviewed here: Y17+ (delta agent). Evidence addresses are unslid cache addresses. Verdicts: VERIFIED, FIXED (sha), DEVIATION (documented), DEFECT-OPEN.

Fix commits of this review: 61c409b (Y3), 34b38ee (Y4), d5fe332 (Y8), 18897f2 (Y13), 372794f (Y15), 953596a (Y16).

## Answers to the explicit questions

* **Y5 y5_classicsize and the portrait moved window.** 16.2 `+_defaultLaunchingSizeForDisplayConfiguration:classicMode:` 0x1c733bc90: mode -1 or 0 -> `[config bounds]`; modes 1..16 -> the iPhone size table row; there is no display test at all (16.0 0x1c5ec8834 additionally required `[[config identity] isMainRootDisplay]`). The only caller is `-[SBApplication defaultLaunchingSizeForDisplayConfiguration:]` 0x1c733857c, which passes `[self _classicMode]` (0x1c7338730: stored override, else `_classicModeFromSupportedTypes`, -1 -> 0). `_classicModeFromSupportedTypes` returns 0 / -1 for every application that supports the iPad (device class 2 branch, `_supportsApplicationType:2`, `_bypassesClassicMode`), so the table is reached for iPhone-only (classic) apps only. The hook keeps modes -1 / 0 on the real configuration and only substitutes the embedded display's configuration for a classic mode on a non-main config, which is exactly the 16.2 result (the table does not read the configuration). **It cannot make an iPad-native window portrait, neither for a normal open nor for Move to Display.** An iPhone-only app is iPhone sized (portrait) in 16.2 too. VERIFIED.
  The 16.2 `-[SBDeviceApplicationSceneHandle _modifyApplicationSceneSettings:fromRequestContext:entity:]` 0x1c729dfb4 has an additional external display classic branch (restricted classic configuration of `[a2 displayConfiguration]` when `[sb_displayIdentityForSceneManagers isExternal]`, gated by `supportsChamoisOnExternalDisplay` instead of 16.0 `isChamoisLinked`, an SDK link flag). That branch is the "S1" blocker of the sweep (no SDK linkage flags in 16.0), it only concerns apps that are not linked against the new SDK, not the user's iPad-native windows.
* **Y8 y8_extorient.** 16.2: `-[SBLayoutState interfaceOrientation]` 0x1c7291884 returns the ivar (+8) when non zero, else tail calls the INSTANCE method `_defaultInterfaceOrientation`; `-[SBMainDisplayLayoutState _defaultInterfaceOrientation]` 0x1c7721500 answers Portrait (1) when `isDisplayExternal`, else `[SBApp activeInterfaceOrientation]`. `_isDisplayExternal` (ivar +0x3a) is set by the state initialiser from the request's display. Only a state WITHOUT its own orientation is affected: `_layoutStateForApplicationTransitionContext:` (0x1c72952ec) calls `setInterfaceOrientation:` on every state it builds (16.0 and 16.2), so after a transition the answer is the computed orientation; the portrait default is seen by initial states and by reads between init and set. The port derives `isDisplayExternal` from `displayOrdinal == 1`; main display states are untouched. VERIFIED.
* **Y10 auto PiP, source 11.** 16.2 0x1c76bfe88 has no source test (candidate = first previous entity that is an application scene entity and passes `_doesPegasusAllowEntityToAutoPIP:`). Skipping source 11 (all gesture transaction requests, CORE-LEFTOVERS P7) is a DEVIATION that was added deliberately: a window dragged to the other display must not be taken for a window leaving into PiP. Cost: a Home gesture on a Stage Manager display does not start PiP for a video that is not the role 1 window (the 16.0 path still decides those requests as before). Documented in the file header.
* **Y16 y16_shotcorner.** 16.2 0x1c77934fc: for `SBCornerFingerPanGestureRecognizer` the touch type mask is `chamoisWindowingEnabled ^ 1` (0 when Stage Manager is on), for the pencil recognizer 2; each corner is armed when `(configured touch types & mask) != 0` (16.0: mask 1 / 2 fixed). With Stage Manager on the finger mask is 0, so a finger swipe from a bottom corner never starts the screenshot / quick note gesture. The hook does exactly that (finger recognizer only, pencil unchanged). VERIFIED.
* **Y13 y13_failgestures.** 16.2 0x1c73136e0 adds `_unpinSplitViewApplicationGestureRecognizer setEnabled:NO` / `YES` after the scrunch recognizer reset. The hook is the same two calls after the 16.0 body. VERIFIED. (Callers that fail all multitasking gestures during a window drag end the drag in 16.2 too.)
* **Y6 portal lifetime (ghost windows).** The type 4 overlay is created by `_updatePortaledSceneLiveContentOverlays` only while the dragged event is a continuous expose window drag whose source controller is not this display, is kept in `_appLayoutToLiveContentOverlayContext` and is removed by the same method (block 0x1c74ce650: every type 4 context whose layout is not the converted one) on transitionDidBegin / End, appLayoutWillBecomeVisible / DidBecomeHidden, and by `_removeOverlayForAppLayout:animated:` (type 4 now handled like 1 and 2: content view controller removed, `invalidate`). The portal view only references the source scene content view (`sourceView`), nothing in Y6 retains a scene or window beyond that overlay. Begin / End skip the update while live content updates are suspended (16.2 early exit, 0x1c74ca5c8 / 0x1c74cb28c), Visible / Hidden call it unconditionally (0x1c74cc2ec / 0x1c74cc384). Identical to 16.2. The G3B overlay class (`invalidate` is an empty method in 16.2 as well, 0x1c78a67a0) is not mine. A remaining ghost after a drag back therefore comes from the drag completion plumbing (P1Drag / G1D), not from Y6. VERIFIED.

No defect was found in Y5 / Y8 that explains the portrait moved window or the rotated keyboard: the Y hooks that touch orientation (y8_extorient, y16_snaporient, y15_bannerorient) match 16.2 and are inert for an iPad-native window moved with Move to Display. The Move to Display take-over is P1Drag (`p1_toappstake`) and the orientation data path is Z2Orient / UIK, not Y.

# POINTER-PIXELS-0.7.4: stale pixels on the extended display's edge when the pointer leaves it (real iPadOS 16.0 pointeruid vs 16.1 / 16.2, ExtendedDisplayEnabler 0.2.2)

Static analysis only. Tags: [H] read from code, [M] inferred from code, [L] guess / not checkable statically.
Supersedes the assumption in POINTER-CROSS-0.7.4.md that "16.0 pointeruid == 16.1" ([L] there): it is false, see section 3.

## 0. Verdict

1. [H] The user's real 16.0 pointeruid is NOT identical to 16.1 / 16.2. The display-transition / hide path IS identical in all three: `_movePointerToDisplay:`, `hidePointer`, `_hidePointerForReason:`, `_restartAutohideTimer`, `pointerEventStreamProvider:didReceivePointerEvent:`, `_displayContextForPointerEventContextID:`, `_invalidateEffectSourcesPassingTest:displayContext:`, `displayDetached:`, the controller's `_updatePointerWithOptions:`, the rendering controller's `setPointerState:options:...` (section 2). There is no edge clamping and no edge handling in pointeruid in any build (clamping lives in backboardd; pointeruid imports no clamp/edge call, only `CGRectContainsPoint` for hover-region hit tests).
2. [H] The real 16.0 pointeruid DOES lack four multi-display changes that 16.1 has (all kept in 16.2): (a) the pointer shape view's own layer is a `CABackdropLayer` in 16.0 only; (b) the pointer rendering view is hidden "for performance reasons" when the display has a system pointer scene, 16.0 draws it always; (c) nil-system-scene handling in `displayAttached:`; (d) accessibility pointer zoom per display. 16.2 adds only `feather` and `_transformForLayer:inContext:` over 16.1 (section 3).
3. [L] Which of these, if any, produces the stale pixels cannot be proven statically. Candidates ranked in section 4. The glitch may also be present on stock 16.1 / 16.2 (nobody has checked: the whole "16.2 fixes it" premise is unverified).
4. [H] ExtendedDisplayEnabler does not touch pointeruid, backboardd, QuartzCore, CoreDisplay, IOMobileFramebuffer or the display configuration. It is a SpringBoard-only tweak with 5 `MSHookMessageEx` hooks on SpringBoard classes (section 5). It cannot be the cause by itself; what it does is make SpringBoard host an Extended-mode display, which is what gives the extended display its own pointeruid display context (rendering window + system pointer window). The glitch with EDE alone therefore only proves the cause is in stock 16.0 code (pointeruid / compositor / display pipeline), not that 16.2 fixed it.
5. Portable: yes, a small pointeruid-side tweak can reproduce the two 16.1 pixel-path changes (section 6). Not verified on device; confidence that it removes the stale pixels: LOW (about 25 %). If it does not, nothing portable is left in pointeruid (everything else is byte-identical to 16.2) and the remainder is QuartzCore / DCP, not portable.

## 3. Every real difference 16.0 -> 16.1 -> 16.2 [H for the code facts]

16.0 -> 16.1 (kept in 16.2), the non-noise changes group into 4 items:

1. **`+[PUIDPointerShapeView layerClass]` removed.** 16.0 0x1000054b8 = `ldr x0,class_CABackdropLayer; b objc_opt_self`, i.e. each `PUIDPointerShapeView` (the pointer, plus the `_specularEffectMaskPointerShapeView` copy) has a `CABackdropLayer` as its own layer. 16.1 / 16.2 have no such method (plain `CALayer`); only `PUIDPointerShapeBackdropView layerClass` (child backdrop views, 16.0 0x100004384 / 16.1 0x100004180 / 16.2 0x100003eb0) and `PUIDShapeView layerClass` remain. The code that uses the outer layer is unchanged: `initWithFrame:` (16.0 0x100004390, 16.1 0x10000418c) does `[self.layer setFilters:@[CAFilter gaussianBlur named "gaussianBlur"]]` and `setBlurRadius:` writes `layer.filters.gaussianBlur.inputRadius`, which the hide / show animation drives (`visibleToHiddenPointerBlurRadius`). Effect: in 16.0 that gaussian-blur filter sits on a backdrop layer (filters the backdrop behind the view's bounds, NOT the pointer's sublayers); in 16.1+ it sits on a plain layer (blurs the composited pointer subtree, including the child backdrop views). Whether the outer view has non-zero bounds in 16.0 was not determined [L] (no `setBounds:` / `setFrame:` on `_pointerShapeView` found in the shape view or the update path, only `setPosition:`), so the outer backdrop may be zero-sized and harmless.
2. **`hiddenForPerformanceReasons`** (new ivar `_hiddenForPerformanceReasons` +0x138 of the rendering VC, `initWithDisplay:` 16.0 0x10001e914 -> `initWithDisplay:hiddenForPerformanceReasons:` 16.1 0x10001e7f0 / 16.2 0x10001e664). `-[PUIDDisplayContextFactoryImpl newDisplayContextForDisplay:pointerRenderingScene:systemPointerScene:]` (16.0 0x100010c4c, 16.1 0x100010ac8 `cmp x20,#0; cset w23,ne` at 0x100010b60, 16.2 0x10001093c) passes `hidden = (systemPointerScene != nil)`; `PUIDPointerRenderingRootViewController viewDidLoad` (16.1 0x10001e9dc, `[self.view setHidden:_hiddenForPerformanceReasons]` at 0x10001ea70) hides the rendering root view. SpringBoard prepares both the rendering scene and the system pointer scene for every display (`PSPointerSystemClientController prepareScenesForPointerForDisplayConfiguration:` 16.0 0x1c693ba90 calls `_prepareSceneForIdentifierPrefix:` twice, 0x1c693bb48 / 0x1c693bb60), so in 16.1+ the direct pointer rendering is hidden on every display that has the system window, and the pointer is only visible through the system pointer window's `_UIPortalView` [M: portals of a hidden source layer keep rendering, not verified]. 16.0 draws the pointer both directly and through that portal (two stacked backdrop / blur trees at the same place) [M]. 16.1 also logs "skipped creating system pointer window" (new string) when there is no system scene.
3. **`displayAttached:pointerRenderingScene:systemPointerScene:`** (16.0 0x100008060, 16.1 0x100007ee0, 16.2 0x100007d40): 16.1 wraps the system-client portal-source-collection setup in `cbz systemPointerScene` (16.0 assumes the system scene exists); the rest (creating `PSMutablePointerHoverRegion`, `setShouldBeInvalidatedIfPointerLeavesDisplay:NO` for the system client's collection, `_movePointerToDisplay:` for the first display) is equal. Effect only for a display without system pointer scene.
4. **Per-display accessibility pointer zoom**: `_axPointerZoomScaleFactor` (16.0 0x100006314 / 16.1 0x100006104) `inStandbyMode` -> `window.screen.displayIdentity.displayID` + `inStandbyModeOnDisplay:`; `_axRegisterForZoomUpdatesIfNecessary` (16.0 0x100006bec / 16.1 0x100006a24) `registerForZoomAttributes:updatesImmediatelyWithChangedHandler:` -> `...onDisplay:...`. Only matters with Zoom enabled.

16.1 -> 16.2 (all of it new `feather` material work, nothing about displays): `PUIDPointerShapeView` +`feather` / `setFeather:` (0x100004854) / `presentationFeather`, `initWithFrame:` (+23 instr: two `UIViewFloatAnimatableProperty` for feather and intensity), `setIntensity:` (+5), the show / hide blocks blk13 / blk14 gain `setFeather:`; `PUIDPointerController _transformForLayer:inContext:` (16.2 0x10000fd74) replaces `BKSHIDServicesGetCALayerTransform` in `_getTransformForHoverRegion:completion:` blk1 (16.1 0x10000d174 / 16.2 0x10000cfd4: now skips when `_systemPointerInteractionContextByDisplay` has no context).
Strings only in 16.1/16.2: `_hiddenForPerformanceReasons`, `skipped creating system pointer window`, `inStandbyModeOnDisplay:`, `displayID`, `displayIdentity`; only in 16.2: `feather`, `setFeather:`, `presentationFeather`, `_transformForLayer:inContext:`. Nothing removed except `layerClass`, `initWithDisplay:`, `inStandbyMode`, the old zoom registration selector.

Frameworks: the user's PointerUIServices / PointerUISystemServices Info.plists are the 16.0 ones (PointerUIServices `DTSDKBuild 20A8371`); their code is the dyld-cache copy already compared (identical 16.0 vs 16.2 per POINTER-CROSS). `Assets.car` (47400 bytes, sha256 cee557a2...) was not compared with 16.2 (no 16.2 copy extracted) and holds no layer or compositing code [L: not opened].

## 4. Which delta could produce the artifact (ranked) [L unless noted]

Observed: clipped pale circle -> pink / cyan / white fragments on the cut line for a few frames -> small dark rectangles >= 0.5 s -> a few cyan / green specks. The hide spring (blur, scale, intensity, alpha) starts when the first event of the other display arrives, with the pointer clamped on the edge, half outside.

1. **Compositor / display pipeline clipping backdrop layers at the display edge (QuartzCore, DCP)**: pink / cyan / green fragments and persistent small rectangles look like uninitialised or wrong-format backdrop buffers, not like geometry; every pointer layer involved is a backdrop (`PUIDPointerShapeBackdropView`, the child `_pointerView` with colorMatrix, `_shapeMorphingBackdropView`, the 19x19 `_UILumaTrackingBackdropView`, the portals). All of that code is identical in 16.0..16.2, so if 16.1 / 16.2 do not show the artifact the cause is not here; if they do, it is stock and not portable. Not diffable (QuartzCore has no cursor / pointer delta; IOMobileFramebuffer strings equal).
2. **Direct + portal double rendering in 16.0 (item 2 of section 3)**: the only delta that removes a whole composited tree on the display that is being left. [M that it halves the backdrop work at the edge; L that it matters for the artifact].
3. **Outer `CABackdropLayer` (item 1)**: a blur-filtered backdrop whose bounds straddle the display edge while its radius animates is a classic edge artifact (blurred backdrop sampled outside the display), but its bounds may be zero (see above); and in 16.1+ the same filter acts on the pointer subtree instead, which could just as well be the better or the worse case.
4. Items 3 and 4 (nil system scene, zoom): not applicable to a normal extended display with Zoom off.

Exact claim: no code in pointeruid 16.0 differs from 16.2 in the hide / transition / teardown logic; only the layer setup it acts on differs.

## 5. ExtendedDisplayEnabler 0.2.2 [H]

* Package: `com.infernowolf19.extendeddisplayenabler` 0.2.2, `iphoneos-arm64`, Description "Re-registers the Extended display provider that iPadOS 16.0 (20A8372) SpringBoard no longer creates", Depends mobilesubstrate. One dylib (universal arm64 + arm64e, 169568 bytes) + plist filter `{Filter: {Bundles: [com.apple.springboard]}}`: loaded into SpringBoard only.
* Imports: libobjc, Foundation, CoreFoundation, UIKit, libSystem, CydiaSubstrate (`MSHookMessageEx` only, no `MSHookFunction`), `dlopen` / `dlsym` for libroot. No QuartzCore, CoreDisplay, IOKit / IOMobileFramebuffer, BackBoardServices or PointerUI symbol or string; no "AirPlay", display scale, resolution (2560 / 1440), `CAWindowServer` or cursor / pointer strings other than `_mousePointerManager`.
* The five hooks (sub 0x4b90): `SBDisplayManager registerDisplayControllerProvider:` (early insertion of the Extended provider, `SBSceneHostingDisplayControllerProvider` built from `SBSystemShellExtendedDisplayControllerPolicyFactory` + `SBSystemShellExtendedDisplayResolverFactory`; log "registered Extended display provider"); `SpringBoard _completeStartupAfterMainSceneConnect:` (fallback install, retries "gave up after %d attempts"); `SBExternalDisplayService setDisplayMirroringEnabled:forDisplay:` (default / saved choice mirror vs extended, "beta-5 default", 1 s verification log); `SBSystemShellExtendedDisplayControllerPolicy connectToDisplayController:displayConfiguration:` (`setExtendedDisplayEverEnabledWithHardwareReqsSatisfied:`, `_areRuntimeAvailabilityRequirementsMet`); `SBExternalDisplayEducationObserver displayManager:didConnectToRootDisplay:` (exception guard). `mousePointerManager:` is only passed to the policy initialiser. Crash guard / kill switches: `bootStrikes` default, `<jbroot>/tmp/ExtendedDisplayEnabler.off`, `.debug`, log `/tmp/ExtendedDisplayEnabler.log`.
* Conclusion: the extended display, its 2560x1440 mode, scale, pixel format and the compositing path are stock iPadOS 16.0 + a real Stage Manager-style display controller; the pointer layers go through the normal display pipeline. EDE's only indirect link: windowing mode of the display decides whether SpringBoard prepares pointer scenes for it (`SBMousePointerManager _updatePointerAssertionsAndScenes`, 16.0 gate `sb_displayWindowingMode == 1`, POINTER-CROSS 2.2), and that creates the extended display's own pointeruid context. Nothing in EDE plausibly explains stale pixels [H for "no relevant code", M for "no indirect effect"].
* Context that fits the finding: the 16.0 (20A8372) SpringBoard has no Extended provider (EDE's description), i.e. the extended-display pointer path of stock 16.0 pointeruid was never exercised by a shipped 16.0; the four pointeruid multi-display changes of section 3 are exactly the polish Apple added for the 16.1 launch of the feature [M].

## 6. Portable fix (pointeruid-side tweak; not in the repo, not tested) [L for effect]

New target process `pointeruid` (MobileSubstrate filter `Executables: ["pointeruid"]`, same mechanism as the existing backboardd filter; Dopamine daemon injection assumed to work as for backboardd [M]); kill switches `Backport162.off.pointeruid[.layerclass|.hidden]`, userspace reboot / `killall pointeruid` after install.

```
// 1. 16.1 behaviour: plain layer for the shape view (16.0 0x1000054b8 returns CABackdropLayer)
%hook PUIDPointerShapeView
+ (Class)layerClass { return [CALayer class]; }          // == UIView default, what 16.1/16.2 effectively do
%end

// 2. 16.1 hiddenForPerformanceReasons (factory 16.0 0x100010c4c; view is loaded when the factory returns because the window is un-hidden inside it)
%hook PUIDDisplayContextFactoryImpl
- (id)newDisplayContextForDisplay:(id)d pointerRenderingScene:(id)rs systemPointerScene:(id)ss {
    id ctx = %orig;
    if (ss && [ctx systemPointerRenderingController])
        [[[ctx pointerRenderingController] view] setHidden:YES];   // 16.1: viewDidLoad setHidden:(ss != nil)
    return ctx;                                                    // new/alloc rule: this is a "new" method, returns +1 as orig
}
%end
```
Order / constraints: hook 1 must be installed before the first `PUIDPointerShapeView` is created (tweak constructor runs before the scenes connect); hook 2 first needs the portal path of the system window to actually render the pointer on 16.0 [M that it does: 16.0 `displayAttached:` builds the same `createPointerPortalSourceCollectionForClient:` + `setSystemPointerPortalSourceCollection:` chain]. RISK of hook 2: if the portal of a hidden source does not render on the 16.0 build, the pointer disappears on every display (hence the separate kill switch). 16.1+ additionally has the nil-system-scene guard (item 3), irrelevant here. Items 4 (zoom per display) and 16.2 `feather` are not needed for the artifact (feather is a visual change of the material; porting it needs the new animatable properties, skip).

If after hook 1 + 2 the artifact is unchanged, nothing portable remains: the rest of pointeruid equals 16.2 and the cause is below pointeruid.

## 7. Probes that settle it (device)

1. **Where do the pixels live**: right after the glitch, `killall pointeruid` (launchd respawns it, SpringBoard re-prepares scenes): rectangles gone at once = layers owned by pointeruid (backdrop state of the old display); still there = framebuffer / damage tracking (QuartzCore, DCP). Second check: drag a window across the bottom edge of the monitor; if the stale rectangles vanish only where something redraws, it is a missing-damage problem, not an extra layer.
2. **Freeze test**: `kill -STOP $(pidof pointeruid)` while the pointer is on the monitor, move the mouse off the display, `kill -CONT` afterwards; if the artifact appears only after CONT, it is produced by the hide animation, not by the compositor on cross.
3. **Same edge without a display change**: move the pointer to the bottom edge of the monitor and stop (clamped, half out, then back): the artifact on the clamped half alone would be a pure edge / backdrop clipping problem. Also leave the iPad through its top edge into the monitor (stale pixels on the iPad edge?) and, if possible, let a second 16.1 / 16.2 device or a 16.2 build of the user's own setup show whether the artifact exists there.
4. **os_log of pointeruid**: subsystem `com.apple.PointerUI` (string in PointerUIServices, 16.0 cstring 0x191b51a7f), categories `Common`, `Autohide`, `Material`. Predicate `subsystem == "com.apple.PointerUI" OR process == "pointeruid"`. Capture with Console.app on a Mac (USB iPad, "Include Info / Debug Messages"), `idevicesyslog -p pointeruid` or the jailbreak `oslog`. Lines that bracket the event (identical 16.0..16.2): "Got a pointer event with contextID: 0x%x and the last event had contextID: 0x%x, moving pointer to display: %{public}@", "Moving pointer to display: %{public}@", "Hiding pointer: %{public}s", "<%{public}@> detaching display was NOT the active display", "created source collection on active display / on display %{public}@", "invalidated source collection: %{public}@", "%{public}@ - Notifying client portalSourceCollections were invalidated: ...". Expectation: one "moving pointer to display" and one "Hiding pointer" per crossing, no "detaching display" lines (the display stays attached). A second "Moving pointer" back to the monitor within the artifact time would point to event ping-pong (backboardd side, cf. POINTER-CROSS pointeruid routes).
5. **A/B with the tweak of section 6**: three runs (layerClass only, hidden only, both) with the same recording; each switch is independent. This is the decisive probe for items 1 and 2.
6. Compositor side (not in pointeruid): `subsystem == "com.apple.QuartzCore"` and `process == "backboardd"` around the event in the same capture; any "backdrop" / "surface" / "display" warnings with the timestamps of the cut-line fragments.

## 9. Implementation decision (PTR.x, Backport162PTR dylib) [not built / not run on a device]

Implemented as a third dylib of the main package (`PTR.x`, `Backport162PTR.plist` filter `Executables = pointeruid`, arm64e, kern.osversion 20A8372 only, process name checked again in the constructor). Deviations from the section 6 pseudocode, all deliberate:
* Hook B is not on the factory: `newDisplayContextForDisplay:...` is a `new` method (ARC +1 rule, a logos hook would leak one display context per attach). Instead `-[PUIDDisplayContext setSystemPointerRenderingController:]` (called by the factory right after `setSystemPointerWindow:`, 16.0 0x100010df4 / 0x100010e00, and after the rendering window was un-hidden with the root view loaded, 0x100010d44) hides `pointerRenderingController.view` when the controller is non-nil and `systemPointerWindow` is non-nil, i.e. exactly when 16.1 has a system pointer scene. Nothing in 16.0 unhides that view again (checked: the only `setHidden:` in the rendering VC outside `viewDidLoad` blocks touches the specular image).
* Hook C is two hooks: `PUIDSystemPointerWindow initWithWindowScene:nil` returns nil (16.1 factory skips the window; the unused 16.0 system controller stays, one leaked alloc in a path SpringBoard never takes) and `displayAttached:` with a nil system scene runs the 16.0 code while `createPointerPortalSourceCollectionForClient:` answers nil (thread-local flag), which reaches the same state as 16.1's `cbz` (the nil collection only goes to nil-safe setters). Not a line-by-line copy of 16.1's `displayAttached:` (re-implementing 250 instructions of private API is riskier than the flag).
* Hook A is `+layerClass -> [CALayer class]`; installed only if `PUIDPointerShapeView` has its own `layerClass` (16.0 does). Per-display AX zoom is not ported (needs Zoom on; not related).
* Install: tried in the constructor and then every 50 ms on the main queue (max 100 tries) until the three class groups exist; a group is skipped with a log line if a class or selector is missing.
* Switches (any `access()` failure = on; looked up in `/var/jb/tmp` and `/tmp`, cached 1 s): `Backport162.off.ptr_layerclass`, `.ptr_hidden`, `.ptr_scene`, `Backport162.off`. They are read when a shape view / display context / display attach happens, so create the file and `killall pointeruid` (or reconnect the display) to see the change.

Risks on a device: (1) the pointer disappears on every display if portals of a hidden source do not render on the 16.0 build (hook B; B's whole premise is [M]) -> `touch /var/jb/tmp/Backport162.off.ptr_hidden; killall pointeruid`; (2) different look of the hide blur / pointer material (hook A, 16.1 look); (3) pointeruid crash-loop (launchd respawns it; a crash would be in the hooks, check for `[Backport162PTR]` lines and a pointeruid ips in Settings > Privacy > Analytics) -> `touch /var/jb/tmp/Backport162.off` and `killall pointeruid`, or remove the package; (4) Dopamine may not inject into the pointeruid daemon (then nothing happens and there is no `[Backport162PTR] loaded` line). First check after install: that line, `ptr_layerclass installed`, `ptr_hidden installed`, `ptr_scene installed`.

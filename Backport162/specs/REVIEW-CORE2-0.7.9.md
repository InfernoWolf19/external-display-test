## 2. The flagged questions

**Q1 p1_endbcast (deviation, G1D `fluidSwitcherGestureManager:didEndGesture:` + `P1_EndBroadcastBegin/End`): deadlock or open transaction?**
No deadlock: no lock, semaphore or wait is involved; the hold is a thread-local pointer (`tEndBcast`) plus an associated flag, and it lives exactly inside the synchronous extent of the broadcast (`Begin` ... `End` on the same stack). What the hold does: the completion block 0x1c74af778 (re-decoded: `if state not in 1..2 && no animationController -> finishWithCompletionType:1, else refresh the active layout state map; then _finalRootTransaction = nil`) is replaced by "set flag" while `tEndBcast == txn`; `End` finishes the transaction when (flag set) and (still the running transaction) and (no animation controller) and (no `_finalRootTransaction`) and (not interrupted).
Display's complete refused: P1_HandleCompleteBody returns without creating an animation controller (interrupted / nil workspace request / nil controller): then at `End` there is no animation controller and no final root transaction -> `finishWithCompletionType:1` runs, so the transaction is NOT left open. If the second display's complete DID start an animation controller, `End` leaves the finish to that controller's own final root transaction (its completion block runs outside the broadcast when asynchronous, inside it when synchronous, and then the flag is set again and `End` finishes). A complete that is never delivered at all (the case the deviation exists for) ends with `End` finishing: identical to the pre-deviation behaviour, no worse. Residual: (a) an Objective-C exception thrown inside the broadcast would leave `tEndBcast` pointing at a dead transaction (fatal in SpringBoard anyway); (b) fixed C3 (p1_share off). The pre-existing deviation (b) of P1Drag.m (nil animation controller from the coordinator is a logged return where 16.2 asserts) leaves the transaction open until the next touch interrupts it; never seen in any log ("nil animationController" count 0), left as is and documented here. 16.2 has no hold: its serial per-display completes never finish the transaction before the second display's complete because the final root transaction of the first complete is not synchronous there. Verdict DEVIATION (documented, device evidence u7/u9).

**Q2 P1_ToAppsPerform: whose instances? non-menu launches?**
Installed on `SBToAppsWorkspaceTransaction` itself (16.0 `-transaction:performTransitionWithCompletion:` 0x1c5e3e06c). The gesture transaction is NOT a subclass (`SBFluidSwitcherGestureWorkspaceTransaction : SBSystemGestureWorkspaceTransaction`, class dump), and it overrides the method itself (P1_Perform), so it is not affected. Affected: SBToApps and its five subclasses present in 16.0: SBAppToApp, SBAppExited, SBActivateAppUnderLockScreen, SBCoverSheetToApps, SBTransientOverlayDismissAllToApps (unless a subclass overrides without calling super). 16.2 runs the identical block for EVERY non-ancillary layout transaction whose request has `toApplicationSceneEntities` (re-decoded 0x1c72b0460: `containsObject:` skip, `toApplicationSceneEntities count`, window scene of `[txn displayIdentity]`, `isChamoisWindowingUIEnabled`, `enumerateSceneManagersWithBlock:` block 0x1c784e3f8 = for each manager != target: for each entity: scene `identifier` == `[[entity sceneHandle] sceneIdentifier]` -> `takeScene:fromSceneManager:`, `existingSceneHandleForScene:` cast to SBDeviceApplicationSceneHandle, `setWantsEnhancedWindowingEnabled:`). So yes: it runs for launches, exits, unlocks as well. For an ordinary launch it finds nothing (a scene lives in exactly one manager; the manager of the request's display is skipped), so no behavioural difference except when the same scene identifier exists in another display's manager, which is the move case. Fixed C2 (the ancillary skip). Block order (outer entities, inner scenes in 16.2; outer scenes, inner entities in the port) is result-equal; the port iterates a copy of `allScenes` like 16.2.

**Q3 PV_ContainerEnd install order vs G3's hook (`layoutStateTransitionCoordinator:transitionDidEndWithTransitionContext:` on SBMedusaDecoratedDeviceApplicationSceneViewController)**
Chain, from the sources: `%ctor` (Tweak.x) runs `G1D_Setup()` (-> `P1Drag_Setup()` -> `P1VC_Setup()`: `class_replaceMethod`, original IMP saved in `sCtrEnd`) BEFORE `BP_G3_Setup()` (-> `%init(G3_DecoratedVC)`, a Logos `%hook` = MSHookMessageEx). The class defines the method itself in 16.0 (class dump). MSHookMessageEx captures the CURRENT IMP as `%orig`, which is `PV_ContainerEnd` (installed first). Runtime chain: G3 hook (`%orig` first, then the zoom-title log) -> PV_ContainerEnd (calls `sCtrEnd` = the 16.0 body first, then the p1ctr log) -> 16.0 body. Both run, G3 outermost, in that order. Nothing re-installs between them (Y6 hooks `SBFullScreenSwitcherLiveContentOverlayCoordinator`, G4B hooks the coordinator class; neither touches this class). Fragile only if G3 were moved before G1D in the `%ctor`: then `class_replaceMethod` would still capture G3's IMP as `sCtrEnd` and both would still run (replace-then-hook or hook-then-replace both chain). Verdict VERIFIED.

## 4. Interaction with Y18IndirectPan / Y19PanDelegates (G1D strip reveal recognizer)
`G1D_MakeStripIndirectPan` builds an `SBIndirectPanGestureRecognizer` (16.0 long init form with the scene's system gesture manager, delegate = gesture manager, `shouldRequireGestureToStartAtEdge:YES`, hysteresis, translation adjustment block). Y18 replaces the hover state machine of the CLASS (`_hoverEntered/Moved/Exited/Cancelled`, `_resetTranslationState`), Y19 adds the hover-only type filter (`_shouldReceiveEvent:` NO for non hover events) and delegate answers for the dock / control centre. Consequences for G1D, no conflict found: (1) the reveal pan now ENDS (state 3) when the pointer leaves the window / display (Y18 `Y18_Ended`), which reaches `_handleContinuousExposeStripRevealGesture:` -> `G1C_RevealRecognizerEvent` as a normal end; the reveal end test `reason == 3 || progress >= 0.25` reads `indirectPanEndReason`, which `Y18_Ended` does not set (16.2 does not either), so a pointer-exit end decides by progress; (2) `reqEdge == YES` with a mouse requires the pointer to have rested 0.25 s at the edge before a second pan (Y18 Possible -> Began), which is the 16.2 behaviour the G1D recognizer already asks for; (3) the touch cancel on a Began -> Changed move now goes to the display of the container view (monitor) instead of the iPad. Open for the Y-family reviewer: Y19 refuses every non-hover event for all `SBIndirectPanGestureRecognizer` instances including the G1D one; trackpad two-finger touch-up reaches the recognizer through `trackpadDidTouchUpWithEvent:` (not `_shouldReceiveEvent:`), so no change for the reveal, but only a device test can show it.

## 5. Static state, timers, kill-switch cost
* Strong statics holding UI objects in the owned files: none that retain scenes or windows. `gG1CRevealInitial` (layout value), `gG2HLayout`, `gG2IWatch` (display items) are value objects; weak: `gGestureRoots`, `gG1DLiveEmptyTransitions`, `gG2HVC`, `gG2IVC`, `gG1CRevealInitialMgr`. Associated objects: coordinator -> transaction (cleared at completion), transaction -> maps / sets / blocks (die with the transaction; `kP1PendReq/Mgr` cleared), overflow recognizer -> indirect recognizer (new, same lifetime pair).
* Timers: one `dispatch_after` 3 s in the reveal watchdog (weak captures, sequence guarded), `NSTimer` of the arc swipe delay (invalidated in `P1_TxnDidComplete`, weak self), G2F/G2H/G2I/G3C `dispatch_after` blocks are diagnostics with weak references. No timer outlives its owner.
* Gesture recognizer failure requirements: the one added by `G1D_GM_Update` is now made once per pair; it cannot be undone through public API and does not need to be (the recognizers are not rebuilt).
* `BP_OnName` after 780b69a: pointer keyed lock free table, 2 `clock_gettime_nsec_np` + a few loads per call, ~200 distinct names in a 512 slot table with 8 probes (a new name whose 8 slots are occupied falls to the mutex + linear scan on every call, ~400 strcmp; expected for a small number of names, none on a per-frame path of this review except the P1 helpers, which are cheap at 120 Hz). Per-frame callers: `PV_LayerTransform` (2 calls), `P1_HandleUpdate` (about 4), `PS_DefScale/Frame` (2).
* Log volume: p1 update lines first 4 + every 60th, async line 3 + every 500th, bring-to-front on change, container line on change, missing selector once per pair.

## 6. Interface expectations of P1SW's orientation code towards the orientation re-architecture (Z2OrientTraits / Z2OrientDelegate; not edited here)
P1SW installs (class_replaceMethod, p1_orient): `SBLayoutState` `interfaceOrientationForLayoutElement:` (wrapper) and the new `interfaceOrientationForLayoutElement:unknownAllowed:` / `_interfaceOrientationForElementIdentifier:unknownAllowed:`; `SBApplicationSceneHandle _createApplicationSceneSettingsFromContext:entity:`; `SBSwitcherController` `coordinateSpaceForLayoutElement:layoutState:`, `sceneEntityFrameForWorkspaceEntity:inLayoutState:`, `interfaceOrientationForSceneHandle:`, `_updateAppTransitionContext:withOrientationActuationContext:` (2 argument form). Expectations:
1. Z2Orient must not replace those selectors (it does not today: it owns `switcherOrientation:...`, `transitionDidBegin...`, `_enqueueOrientationTransition...`, `SBTraitsExternalDisplayPipelineManager inputs`, the delegate sanitizer and the dock). If it must, hook with the saved-IMP pattern so both run, and keep the 2 argument `_updateAppTransitionContext:` form (P1SW forwards to the 3 argument form with `!isChamoisWindowingUIEnabled`; Z2O's phone-on-pad rule uses the 3 argument form directly, so the two never conflict).
2. `[SBLayoutState interfaceOrientation]` of every layout state must be a VALID UIInterfaceOrientation (1..4) of the state's own display, set where 16.2 sets it (`_layoutStateForApplicationTransitionContext:`, from `switcherOrientation:` `*outOrientation`). External display: Portrait (1) is correct and is now used as is (C1); main display: the device / traits participant orientation. P1SW substitutes it for the per-element orientation in the coordinate space and in the scene frame (16.2 rule), and rotates between it and `[switcherWindow interfaceOrientation]`: the window orientation must be the scene's orientation (monitor: 1). A value of 0 or > 4 is refused by P1SW (per-element 16.0 orientation, one `p1sw: orient: ... REFUSED` line).
3. The per-element map (`interfaceOrientationByLayoutElementIdentifier`) must contain every element of the state; `unknownAllowed:YES` answers 0 for an element not in the state (used when a scene is created for a display whose layout state does not contain it yet: cross-display move) and the scene settings code then uses the context / scene orientation. An element that is known but unmapped logs once and answers 0.
4. Expected log: `p1sw: orient: layout state orientation O, switcher window orientation W shape ... -> layout state orientation used` once per combination; O != W is normal during a rotation and on the iPad it must settle to O == W; on the monitor O == W == 1. `Backport162.on.p1_orientshape` restores the old shape rule for an A/B test; `Backport162.off.p1_orient` restores 16.0 completely.
5. Rotation sequence the traits flow must keep: layout state with the NEW orientation is created before the switcher window rotates (P1SW then rotates the coordinate space from W to O, as 16.2 does); a Z2O change that updates the window orientation before the layout state exists would make O == W earlier, which is harmless.

## 1. SBSwitcherController traits flow (`Z2OrientTraits.m`, switches `or_traits`, `or_label`)

### 1.1 What 16.2 changed (decoded; 16.0 method address / 16.2 address)
* `-switcherOrientation:elementsOrientations:forTransitionRequest:previousLayoutState:layoutState:` 0x1c6178cec / 0x1c7600950. Called from `-[SBMainDisplayLayoutStateManager _layoutStateForApplicationTransitionContext:]` (16.0 0x1c5e25c38, 16.2 0x1c7298d00) which stores the results with `setInterfaceOrientation:` / `setInterfaceOrientationByLayoutElementIdentifier:` on the NEW layout state: this is the ONLY place where a layout state gets its orientation, for every display (the switcher controller of the request's display answers).
  * `*outOrientation = [_traitsParticipant currentOrientation]` (the switcher participant) in both releases; elements: 16.0 `_currentElementsOrientationsForLayoutState:` (0x1c617b3fc), 16.2 `_orientationsForLayoutStateElements:withAssociatedParticipants:` (0x1c7602ba0) = `_elementsOrientationsForParticipantsByElementIdentifier:` (0x1c7602c8c, `participant.currentOrientation` per element id) + count assertion. Same map.
  * Rule 1, `_canDetermineActiveOrientation`: 16.0 `!inHomeScreen`; 16.2 `inHomeScreen ? old : YES` (ivar +0x89).
  * Rule 2 (chamois): 16.0 `own = inSwitcher ? 5 : 4`; 16.2 `systemGesture || (fromSwitcher && inApp)` -> own 5 and re-evaluate, else `inSwitcher ? 5 : 4`. Non primary / primary overlay policy 3 / 3.
  * Rule 3: non primary overlay policy of the stable-in-app and home paths = `phoneAppOnPad ? 3 : primaryPolicy` (16.0 always 3).
  * `_waitingFollowupTransition` (16.0 +0x79) is gone. 16.0 enqueued the `FollowupRotation` transition inside the method when its flag was set and then waited for it; 16.2 stores the flag in `_needsOrientationReevaluation` (+0x7a) and `-layoutStateTransitionCoordinator:transitionDidBeginWithTransitionContext:` (0x1c76042cc, 16.0 a 3 instruction stub 0x1c617c79c) enqueues the transition with a validator that returns and clears the flag (block 0x1c7604400); the same method sets `_canDetermineActiveOrientation = (toLayoutState.unlockedEnvironmentMode != 1)` and updates the publisher participant.
  * Event label check: 16.0 `isEqualToString:@"FollowupRotation"`, 16.2 `containsString:` (labels got a counter).
  * Actuation context: `accountForSceneState` = 16.0 `!phoneOnPad`, 16.2 `phoneOnPad ? NO : !chamois`; without a context and with a phone app on the pad 16.2 sets rotation animation settings only if the context is not in live resize and the primary delegate has a scene.
  * `-_enqueueOrientationTransitionWithActuationContext:...label:` 0x1c617aa5c / 0x1c760212c: label `"%@-%ld"` with a global counter; the 16.0 guard on `_waitingFollowupTransition` is gone; the app transition context update moved from the builder into the validator block (0x1c760250c). Ported: the label (switch `or_label`); the update stays at build time (16.0 order; only observable when the validator rejects the request, then 16.0 touched a request that never runs).
  * New `-actuateOrientationForTraitsDelegate:withContext:reasons:` 0x1c7601958: `animator = [[self _liveOverlayForTraitsDelegate:d] prepareOverlayForContentRotation]; [self updateOrientationForTraitsDelegate:d withUpdateReasons:r suggestedAnimator:animator actuationContext:c]`. Added with `class_addMethod`.
  * `_noteLayoutStateEvaluationBegan/Ended...` / `_areLayoutStateElements:matchedWithAssociatedParticipants:` / `_invalidateLayoutElementsTraitsParticipants` / `didChangeSettingsForParticipant:context:`: participant bookkeeping of the new assistant (evaluation counter, stale participant invalidation, ivar offsets); bodies decoded and equal in effect to the 16.0 `_evaluatingLayoutStateOrientation` flag + `_createTraitsParticipantsForLayoutElementsIfNeeded:` (the 16.0 helpers are kept, see 1.3).

### 1.2 What was ported
`Z2O_SwitcherOrientation` replaces the 16.0 IMP with the 16.2 body statement by statement: same guards (nil arguments fall back to the 16.0 body which raises the same assertion), same early outs (under UI lock / no participant while locked), same decision tree (`Z2O_Decide`, every branch labelled with its 16.2 address in the code), same order of calls. The ivars of the 16.0 layout are read / written by name (`class_getInstanceVariable`); the one new ivar is an associated object. `Z2O_TransitionDidBegin`, `Z2O_Enqueue`, `Z2O_Actuate` as above.
Log lines: `z2o: swo (main|ext) request '<label>' src N followup F chamois C phoneOnPad P: own policy ... reevaluate R`, `z2o: swo (...) -> container orientation N, element orientations {...}`, `z2o: transitionDidBegin (...): re-evaluation pending, enqueue FollowupRotation`, `z2o: enqueue orientation transition '<label>-<n>'`, `z2o: traits installed ...`.
Guards (never silent): a missing ivar / selector / class logs `z2o: GUARD ...` once and the 16.0 body runs.

### 1.3 Documented deviations
* Participant creation: 16.2 creates the participants in `SBSwitcherTraitsAssistant -createTraitsParticipantsForLayoutElements:outParticipantsByElementIdentifier:outDelegatesByParticipant:outPrimaryDelegate:` (0x1c7d5be20 stub) every time the elements differ, keeps the previous maps otherwise and invalidates participants that are not in the new set (`_noteLayoutStateEvaluationEnded...`). The port calls the 16.0 `_createTraitsParticipantsForLayoutElementsIfNeeded:shouldPerformFirstResolution:NO` (same participants, same delegates, kept in the 16.0 ivars read by `BPG3BTraitsGuide`). Effect-equal for the orientation results; the lifetime of participants of removed elements differs in timing only.
* Update of the app transition context at enqueue time (see 1.1).

### 1.4 Test
Rotate the iPad (all four orientations) in the home screen, the app switcher and with one / several Stage Manager windows; the log must show one `z2o: swo (main)` pair per layout state evaluation with `container orientation` equal to the device orientation and, for a swipe from an app into the switcher or a system gesture, `reevaluate 1` followed by `enqueue FollowupRotation`. ## 2. The display's orientation in the traits flow (switches `or_extinputs`, `or_extreal`)

### 2.1 Correction of the first version
The first version of this section took "all layout states of the monitor say Portrait" for the bug and forced the monitor to a landscape orientation derived from the canvas. That contradicts 16.2: UIScreen `-_connectScreen` (16.0 0x18902b55c / 16.2 0x189161788) sets an external main-like screen to Portrait without notification, `-_boundsForInterfaceOrientation:` never swaps its landscape bounds (16.2 0x1890c7fc0), and `-[SBMainDisplayLayoutState _defaultInterfaceOrientation]` (16.2 0x1c7721500) answers 1 for an external state. A Portrait monitor with a 2560x1440 canvas is the 16.2 state. The code was changed accordingly before it ever ran (commit after ccf3424).
### 2.2 Mechanism
The external window scene has its own traits arbiter (`SBTraitsExternalDisplayPipelineManager`, same class and bodies in both releases: `inputs` 16.0 0x1c616fa60 / 16.2 0x1c75f7740, `setupDefaultPipelineForArbiter:` 0x1c616f898 / 0x1c75f7578). Its only orientation input is `SBFTraitsArbitrationDeviceOrientationInputs initWithCurrentDeviceOrientation:nonFlatDeviceOrientation:` with `[windowScene interfaceOrientation]`, built ONCE (lazy ivar `_inputs` at +0x28) at the first call of `-inputs`; every role of the monitor (switcher, windows, keyboard) resolves against that snapshot. In 16.2 the screen is already Portrait when that happens (`_connectScreen`); in 16.0 the screen orientation starts at 0 (`_interfaceOrientation` ivar) and is set later by scene code, so a snapshot taken earlier is 0 / stale.
### 2.3 Port (`Z2OrientTraits.m`)
`Z2O_ExtInputs` (`or_extinputs`): the cached input is compared with the scene's current orientation on every call and rebuilt (same classes and init selectors as the 16.0 body) when they differ; a scene orientation of 0 becomes 1 (the 16.2 `_connectScreen` value); a valid scene orientation is never rewritten, so the arbiter agrees with the switcher window. Log: `z2o: external display arbiter input kept|REFRESHED: device orientation N (scene orientation M, canvas shape S)`.
`Z2O_GuardExternal` (`or_extreal`, logged last line guard): an INVALID container orientation of an external display's layout state is replaced by the 16.2 value; a valid one is kept. Every external evaluation logs `z2o: ext display state orientation: participant N, scene orientation M, canvas shape S, 16.2 value R [(DIFFERS from the scene)]`. A `DIFFERS` line is the signature of the Move to display rotation on the SpringBoard side (a layout state / element orientation that is not the screen's).
**NEEDS EDIT IN P1SW.m (not made, file owned by the core agent):** `PS_LayoutOrientationUsable` rejects a layout state orientation that contradicts the switcher window SHAPE (landscape <=> wider than tall). For the monitor that rule is wrong under 16.2 (Portrait with a landscape canvas is normal); it should compare the layout state orientation with the switcher WINDOW's orientation instead (`[window interfaceOrientation]`), which is what `coordinateSpaceForInterfaceOrientation:withReferenceCoordinateSpace:inOrientation:` does. Until then the log line `p1sw: orient: layout state orientation 1 contradicts the switcher window shape 2560x1440` is expected on the monitor and the per-element orientation is used there.
**NEEDS EDIT IN Backport162UIK / SpringBoard:** the U1 UIScreen hooks are restricted to apps; 16.2 SpringBoard runs the same 16.2 UIScreen code for the monitor's screen (never swapped bounds, Portrait at connect). Whether SpringBoard's own UIScreen needs the same hooks cannot be decided offline; the `z2o: ext display state orientation` lines (scene orientation column) answer it: scene orientation 3 / 4 on the monitor means SpringBoard's screen is rotated and swaps its bounds.
### 2.4 Unproven
Everything above. The decisive log lines: `z2o: external display arbiter input`, `z2o: ext display state orientation`, `z2o: 16.0 rotation machinery` (names which feature flags are live: 16.0 gates the arbiter orientation actuation behind `os_feature_enabled(SpringBoard, TraitsArbiterActuation)` / `PostModernRotation`, 16.2 removed the flags and the pre modern rotation code; if the line says NO / NO the whole legacy rotation path is live on the device and R1 .. R4 describe a flow that is switched off by the flag).

## 3. SBTraitsSceneParticipantDelegate and the floating dock (`Z2OrientDelegate.m`, switches `or_delegate`, `or_dock`)
Method-by-method diff of the 13 delegate rows (16.0 -> 16.2, call sequences compared, every difference read):
* `_sanitizedMask:forApplication:` 0x1c62d89b0 / 0x1c7773a88: 16.0 narrows a `classicAppPhoneAppRunningOnPad` app to portrait (0x6) or, with `classicAppPhoneOnPadPrefersLandscape`, landscape (0x18); 16.2 only keeps the upside-down rule and `& _allLegalOrientations`. The restriction moved into the guiding participants, which can be LANDSCAPE for a user-resized iPhone window; with the 16.0 restriction such a window can never leave portrait. PORTED (`or_delegate`), guarded: only while `g3b_guide` is on and `BPG3BTraitsGuide` exists (else the 16.0 body runs and one `z2o: GUARD(or_delegate)` line says why).
* `_supportedOrientations`, `scene:didUpdateClientSettingsWithDiff:...`, `_resetToInitialState`, `actuateOrientationSettingsWithContext:`, `didChangeSettingsForParticipant:context:`, `initWithScene:`, `initWithSceneHandle:`: the alter ego (`_supportedOrientationsOverride`, `_startAlterEgoWithDesiredOrientations:error:`, `_checkAlterEgoValidityForUpdateReasons:`, `_resetAlterEgoState`) is replaced by `SBTraitsSceneOrientationRequestAssistant` (new class: `initWithTraitsSceneDelegate:errorDomain:`, `setUpForTransitionContextIfNeeded:`, `checkValidityAgainstUpdateReasons:`, `invalidate`); the two machines answer the same app request (`requestGeometryUpdate` orientation preferences) and 16.2 expresses the supported-mask override as a guiding participant (`_guidingSceneOrientationRequestParticipantWithMask:`). NOT PORTED: the 16.0 alter ego keeps handling scene orientation requests; reason: the replacement needs the guide map entry `_guidingSceneOrientationRequestParticipantsMap` of the assistant, which `BPG3BTraitsGuide` does not have (G3B 1.4 "Not ported"); porting only the delegate half would leave requests unanswered. `initWithScene:` / `initWithSceneHandle:` differ by the removed `_SBPostModernRotationEnabled` assertion only.
* `needsActuationForUpdateReasons:`: 16.0 enumerates the reason bits over `[[participant settings] currentSettings] orientationSettings]`, 16.2 over `[participant settings]` directly (the TraitsArbiter framework accessor changed between the builds). Not ported: the 16.0 framework has the 16.0 accessor and the same enumeration result; unproven equal.
* `sceneContentStateDidChange:`, `updateOrientationSceneSettingsForParticipant:`, `_evaluateOrientationTransitionContext:`, `invalidate`: identical call sequences.
* `SBFloatingDockRootViewController supportedInterfaceOrientations` (16.0 0x1c6336398, removed in 16.2): locked the dock to the window orientation while a presentation transition ran (only when `_SBTraitsArbiterOrientationActuationEnabledForRole(dock)`); `_begin/_endPresentationTransition` (0x1c5e6036c / 0x1c5e61c28 vs 0x1c72d287c / 0x1c72d4114) only lose the `setNeedsUpdateOfSupportedInterfaceOrientations` call in that branch. PORTED (`or_dock`): the override answers the superclass value; the `setNeeds...` calls stay (they re-query the superclass answer).
* `SBWindow initWithWindowScene:...` (16.0 calls `_listenForTraitsArbiterPreferenceChangesIfNeeded` at the end of init, 16.2 does not): the 16.2 listener starts lazily elsewhere; the preference-change listener is an idempotent registration. Not ported; no orientation effect found.

## 4. Not yet ported (reasons, in the order they will be done)
### 4.1 Content / container orientation split of the scene view stack (SBAppViewController, SBSceneViewController, SBDeviceApplicationSceneView, ClassicSupport, live overlay, overlay view provider)
OPEN. Decoded call-sequence differences (16.0 -> 16.2): `SBAppViewController` (6 rows) and the live overlay rows differ only by the API rename `setContentReferenceSize:withInterfaceOrientation:` -> `...withContentOrientation:andContainerOrientation:` (+ `setDelegate:` in `_createSceneViewController`, `initWithApplicationSceneEntity:transitionRequest:delegate:`, the dropped `appView` call); the coordinator's `_configureLiveContentOverlayView:...` passes content AND container orientation; `SBFullScreenSwitcherSceneLiveContentOverlay` moves the touch behaviour update to `_updateTouchBehaviorForScene:` driven by the scene layer manager observer; the only behavioural additions are in `SBDeviceApplicationSceneView` (`layoutSubviews` +67 instructions: frames of overlay views with `needsCounterRotation`, `_anyOverlayViewNeedsCounterRotation` gating the host counter-rotation view, `addOverlayView:withPriority:` reading the window, `dealloc` removing observers). 16.0 already contains the content / container split (`SBOrientationTransformWrapperView`), so with a container orientation equal to the content orientation (every non-rotated window) the 16.2 additions do nothing. Not ported: no code written, because the container orientation argument has no 16.0 consumer and the counter rotation of overlay views only matters for overlays that ask for it (none of the 16.0 overlay views do); the classes and adapters of G3B 1.6 / 1.7 keep the stored values. UNPROVEN whether a rotation glitch of the status bar / home grabber overlays remains.

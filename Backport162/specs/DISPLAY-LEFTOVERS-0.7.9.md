## 1. Per-display keyboard focus locks (`focuslock`, G4B.x group G4B_FocusLock) : PORTED BY ADDRESS

### 16.2 mechanism

`SBWorkspaceKeyboardFocusController` decides which SpringBoard UI may take the hardware keyboard from the app that has it. Two methods of that decision are `objc_direct` in 16.0 and 16.2 (plain C functions `(self, _cmd, arg)`, not in the class method list, listed in the symbol table as "non-external (was a private external)"):

| function | 16.0 | 16.2 | size 16.0 / 16.2 | callers 16.0 |
|---|---|---|---|---|
| `_keyboardFocusPolicyForCurrentUIStateWithAppFocusTarget:` | 0x1c6324e5c | 0x1c77c58c8 | 948 / 972 insns | one: `_updateFocusPolicy` (0x1c6323d88) `bl` at 0x1c6323dc0 |
| `_applyDeferringRulesForPolicy:` | 0x1c6325d8c | 0x1c77c6994 | ~1250 / ~1100 insns | one: `_reevaluatePolicyAndUpdateRulesIfNeeded` (0x1c6321b74) `bl` at 0x1c6321bc0 |

Method-by-method comparison of the two builds (call sequences diffed, then the changed regions read instruction by instruction); everything not listed is the same sequence of calls:

1. `lockFocusToSpringBoardWindowScene:forReason:` (16.0 0x1c6321c94, 16.2 0x1c77c19f0, ObjC visible): 16.2 validates scene (`SBWindowScene`) and reason (`NSString`), keeps `map[reason] = scene` in the new ivar `_windowSceneForSpringBoardFocusLockReasonMap` (0xb8, `strongToWeakObjectsMapTable`) and acquires with `acquireForReason:withContext:scene`; the assertion's state handler (block 0x1c77c1e04) removes the map entries of released reasons. 16.0 keeps ONE weak ivar `_springBoardFocusLockWindowScene` (0xa0) with the last scene and acquires with `acquireForReason:`. `requestFocusStealingForSpringBoardWindow:forReason:` is identical in both builds (sequence diff empty).
2. Policy, lock reasons. 16.2 (0x1c77c5af0..0x1c77c5bf8): `appScene = [windowSceneManager windowSceneForDisplayIdentity:[[appTarget settings] sb_displayIdentityForSceneManagers]]` (nil without a target), `active = [windowSceneManager activeDisplayWindowSceneFollowingUserInteraction]`; for every reason of `[lockAssertions reasons]` the reason goes into the set that makes SpringBoard take focus only when `map[reason] == appScene || map[reason] == active` (pointer comparison `cmp x25,x0; ccmp x26,x0,#4,ne`). 16.0 (0x1c6325050): every reason of `[lockAssertions reasons]` (ivar 0x90) goes in.
3. Policy, window stealing. Both builds reach it only when the reason set is empty. 16.0 (0x1c6325288..0x1c6325520): stealing assertion (ivar 0x98) active; if `_addingSpringBoardPreferredFocusWindowScene` (BOOL 0x40) is set the preferred scene is `orderedContext.lastObject._sbWindowScene` (flag cleared); else with `ext = _lastAcceptedArbiterSceneSuggestion` (0xf0) the first stealing window (set `[stealing context]`) whose window scene's display identity `isEqual:` ext's `sb_displayIdentityForSceneManagers`. 16.2 (0x1c77c5f34..0x1c77c62c4, ext at 0x118) adds, in the non-adding case: `pid = ext.clientHandle.processHandle.pid`; when `pid != getpid()` AND ext's display identity is not the active scene's `_fbsDisplayIdentity`, a stealing window whose scene is the ACTIVE scene (`bs_containsObjectPassingTest:` with block 0x1c77c8b10 = `[[w _sbWindowScene] isEqual:capturedActive]`) makes the preferred scene the active scene itself; otherwise the 16.0 search. (The earlier reading in group4b-reconstruct.md "counts only if its client pid is SpringBoard or the displays are equal" was loose: the real rule prefers the stealing window of the active display.)
4. Apply. 16.2 (0x1c77c6a44..0x1c77c6b08): `active = ...FollowingUserInteraction`; `adviceP = policy.advicePolicy`; if `adviceP == 0` the lock scene is `lastObject` of `[[lockAssertions orderedContext] bs_filter:^(s){ s == active }]` (block 0x1c77c7d68), else nil. 16.0 (0x1c6325e3c): the lock scene is `objc_loadWeakRetained(self + 0xa0)`. The consumers of the lock scene (display compare with the target scene, log lines, preferred scene) are the same sequence in both.
5. `multiDisplayUserInteractionCoordinator:updatedActiveWindowScene:` (16.2 0x1c77c56d8): `if ([lockAssertions isActive]) [self _reevaluatePolicyAndUpdateRulesIfNeeded]`. The controller registers itself as active-window-scene observer in `_init...` when `[externalDisplaySettings activeDisplayTrackingMethodology] == 1`; `settings:changedValueForKey:` (0x1c77c5724) adds / removes it on a change of that key and re-evaluates.

### What was ported (G4B.x section 6b, replaces the former ObjC-level reconcile wrapper)

* Both direct functions are hooked BY ADDRESS with `MSHookFunction` (resolved with `dlsym`), exactly like BBD.x does: the unslid 16.0 address plus the slide of the `SpringBoard.framework/SpringBoard` image; before patching, the 8 prologue words of the function (identical in both: `pacibsp; stp x28,x27,[sp,#-0x60]!; stp x26,x25; stp x24,x23; stp x22,x21; stp x20,x19; stp fp,lr; add fp,sp,#0x50`) AND the `bl` word of the single caller (`0x94000427` at 0x1c6323dc0, `0x94001073` at 0x1c6321bc0, which proves the address is the function that caller really calls) are compared with the bytes of the running image; the hook of a function whose check fails is not installed and `focuslock: <function> prologue mismatch ... not installing` / `caller word ... not expected ... not installing` is logged (also: no `MSHookFunction`, image not found, an ivar missing). The trampoline pointer is re-signed for arm64e like Group4Focus.x.
* Not a rewrite of 2000 instructions: the 16.0 body runs unchanged and receives the 16.2 INPUTS at the exact points it reads them.
  * item 2: the policy hook arms a thread-local context (`kfc`, `appScene`, `active`); `-[BSCompoundAssertion reasons]` (an ordinary ObjC method, hooked) answers, only while armed and only for the focus controller's lock assertion, the reasons whose recorded scene is `appScene` or `active`.
  * item 3: the policy hook evaluates the 16.2 condition itself (stealing active, no adding flag, ext, pid, displays, a stealing window on the active scene). If it holds it sets the `adding` flag for the duration of the call and arms `-[BSCompoundAssertion orderedContext]` to answer `@[thatWindow]` for the stealing assertion: the unchanged 16.0 "adding" branch then yields exactly the 16.2 result (preferred scene = the active scene, policy type 2); the flag is put back afterwards.
  * item 4: the apply hook writes the 16.2 lock scene (advice policy 0: the most recently acquired lock whose scene is the active scene; else nil) into the weak ivar `_springBoardFocusLockWindowScene` (offset checked to be 0xa0) before the 16.0 body reads it.
  * item 1: `-lockFocusToSpringBoardWindowScene:forReason:` is hooked: the map (`reason -> scene`, associated object, `strongToWeakObjectsMapTable` like 16.2) and the acquisition order (stand-in for `orderedContext`, which 16.0 locks do not have because they are acquired without context) are recorded, then the 16.0 body acquires. Released reasons are pruned before each policy / apply evaluation (the 16.2 state handler's job).
  * item 5: the controller gets `multiDisplayUserInteractionCoordinator:updatedActiveWindowScene:` (`%new`) and registers itself at the first `windowSceneDidConnect:` when `activeDisplayTrackingMethodology == 1`; a change of the setting (the `BP162ActiveDisplayTrackingMethodologyChanged` note of G4B_Arrange) adds / removes it and re-evaluates (16.2 `settings:changedValueForKey:`).
* The old stand-in (own request list, proxy tokens, `-_bp_reconcile` on a later runloop turn) is removed: the filter is now evaluated inside the same policy computation as in 16.2 (no one-turn window with the unfiltered state), the real assertions are what callers receive.

Deviations (documented): (a) the lock assertion is still acquired with `acquireForReason:` (not `withContext:`): the context part is replaced by the recorded acquisition order, which is all `orderedContext.lastObject` was used for; (b) the 16.2 map is not an ivar of the controller (a runtime cannot add ivars to the 16.0 class): associated object; (c) the PTSettings key observer / persistence for the methodology is not reproduced (value is session-only, default 1, `methodology0` opt-in as before).

### 2a. SBUniversalControlServer block (16.0 0x1c62d2588 / 16.2 0x1c776d5b8)

`-[SBUniversalControlServer _lock_reevaluateKeyboardFocusDisablement]` (16.0 0x1c62d24d8 / 16.2 0x1c776d508) only dispatches a block to the main queue; the block (captures the server at +0x20, the disabled flag at +0x28) locks the focus to the active display scene (`lockFocusToSpringBoardWindowScene:forReason:"SBUniversalControlServer"`, same in both builds) and suppresses the keyboard: 16.0 `acquireKeyboardSuppressionAssertionWithReason:predicate:nil` (every display), 16.2 (0x1c776d698) `...predicate:nil displayIdentity:[[activeDisplayWindowScene] _fbsDisplayIdentity]`. The block is not hookable by selector, so its INVOKE function is hooked BY ADDRESS with `MSHookFunction`: the 6 prologue words of 0x1c62d2588 and the `adrp x16 / add x16` pair (0x1c62d2550 / 0x1c62d2554) inside the method, which builds the block's invoke pointer, are compared with the running image; a difference logs `[x7] UCS block: prologue / block pointer words differ ..., not installing`. The hook arms the existing one-shot scope (kind S_ACTIVE, identity of the active display scene read at entry, only when the flag byte at block+0x28 is set); the plain acquire inside the block then takes the display scoped route (`X7_OldAcquire`).
Log: `[x7] UCS block hooked at ... : keyboard suppression of SBUniversalControlServer is scoped to the active display`, then per use `[x7] acquireKeyboardSuppressionAssertionWithReason:SBUniversalControlServer for display ...`.

### 2b. OverlayUI requesting focus (`_lock_overlayUIRequestingFocus`, 16.2 ivar 0x28)

New in 16.2, written by `userFocusRequestForScene:reason:completion:` (0x1c77c2c14: when the scene is one of `[[[SBApp systemUIScenesCoordinator] overlayUISceneController] enumerateScenesWithBlock:]`, the same test that makes the 16.0 body store the scene as the high priority scene) and cleared by `removeKeyboardFocusFromScene:` (0x1c77c317c: removed scene's `clientHandle.processHandle.consistentJobLabel` equals the OverlayUI controller's `jobLabel`). Log: `[x7] OverlayUI requests keyboard focus (scene ...)`, `[x7] OverlayUI no longer requests keyboard focus`.

### 2c. `_filterFocusedSceneIdentityToken:focusedPID:resultBlock:` (16.0 0x1c6323f3c / 16.2 0x1c77c4590; 345 -> 443 insns)

Sequence diff of the two bodies: only the "arbiter advice" route differs. ## 6. Clone mirroring transport (client G4B.x `G4B_SendCloneMsg`, daemon BBD.x `BPD_Serve`) : the "reply id 0" line explained and made truthful

Device evidence (0.7.9 logs, `u1/L1.txt`, `3-Backport162.log.1`): the daemon marker shows `install result: updateClone 1 handler 1 ...`, the daemon logs `clone mirror mode request:2 destinationDisplay:... from pid:...`, `updateClone ... prevailing mode 2`, `clone mirror mode remove ...`, and the user confirms that switching mirror / extended works. SpringBoard nevertheless logged on every request `clonemirror: reply id 0 instead of 6004840 (... hook is not installed ...)` and `... 6004841` for the remove request.

### Why the reply id read 0 (proven from the numbers of that log)

`mach_msg(MACH_SEND_MSG | MACH_RCV_MSG, ...)` sends and receives in ONE buffer, its first argument. The old code passed `&req.Head` but read the answer from a different local struct `rep` that nothing ever wrote (zero filled): so `rep.Head.msgh_id` was always 0 and `rep.RetCode` 0, whatever came back. The real reply had arrived and had overwritten `req.Head.msgh_id`: the request ids are 0x5b9fa0 = 6004640 (set) / 0x5b9fa1 = 6004641 (remove), the MIG reply id is request + 100 = 6004740 / 6004741, and the failing comparison printed `req.Head.msgh_id + 100` AFTER the overwrite = 6004740 + 100 = 6004840 and 6004741 + 100 = 6004841: exactly the two numbers of the log (with an untouched request id the line would have said 6004740 / 6004741). So: the daemon half (handler hook, reply built like libdispatch's demux: bits `& 0x1f` = MOVE_SEND_ONCE, id + 100, 0x24 byte reply with NDR and return code) was correct; the check read the wrong memory. No message was lost and the feature worked; only the diagnostic lied. (The earlier review's "an answer CAN arrive" was right; the miss was in the client's receive.)

### What changed (behaviour of the request / reply exchange is unchanged)

* G4B.x: the answer is read from the receive buffer itself (`G4BCloneRep` view of `req`): reply id must be sent id + 100, not complex, at least 0x24 bytes; the MIG code is returned from it (before, always 0, so a daemon refusal such as KERN_NO_ACCESS or MIG_BAD_ARGUMENTS would have been invisible; now it is logged as `refused (MIG code N)`).
* Truthful lines (BP_Log): `clonemirror: >>> SET request for <uuid> mode N (msg id 6004640, size S) sent to com.apple.backboard.display.services`, `clonemirror: <<< reply id 6004740, MIG code 0 after T ms`; failures start with `clonemirror: XXX` and say what failed (`XXX answer is not the reply of this request: msg id N (expected M; 70 = send-once notification = the Backport162BBD handler hook is not installed ...)` is now only printed when the id really differs).
* Bounded retry of the service look-up when the first look-up fails (6 attempts, 250 ms apart, on the serial send queue; logs `attempt N failed kr=...`, `succeeded on attempt N`, and a final `XXX no port ... the request is lost`). Normal case: first attempt succeeds, no delay.
* BBD.x: the daemon logs `clonemirror reply sent: id 6004740, MIG code 0` (or `reply send failed 0x..`, or `no reply port in the request`) next to its existing request line, so one request now shows as: SpringBoard `>>>` -> daemon `clone mirror mode request` -> `updateClone ... prevailing mode` -> daemon `clonemirror reply sent` -> SpringBoard `<<<`.

### Chain facts re-verified (unchanged)
Service `com.apple.backboard.display.services`; request ids 0x5b9fa0 / 0x5b9fa1 are above the stock subsystem (start id 6001000 = 0x5b9168, 16.0 routines end below 0x5b9fa0 per the earlier review); stock handler 0x100026d14 forwards the dispatch_mach message to `dispatch_mach_mig_demux` with the subsystem as context, our handler hook (`reason == 2`, context == subsystem) answers the two ids and passes everything else to the stock handler; message layout 24 header + 8 NDR + 4 length + padded uuid (+4 mode); reply 0x24 bytes.

### Test recipe
With `Backport162.debug`: switch mirroring on / off in Settings > Display. Expect in the log, in this order, for each change: `clonemirror: >>> SET ...`, daemon `clone mirror mode request`, `updateClone ... prevailing mode`, daemon `clonemirror reply sent: id 6004740, MIG code 0`, `clonemirror: <<< reply id 6004740, MIG code 0 after N ms`. Any `XXX` line names the failing step.

## 7. Education alert (`edu`, G4B.x): what the app can show, and the native alert as the automatic fallback

### What was decoded

* The 16.1 app (20B82, extracted too) has the same classes and strings and the same executable size (107824 bytes) as 16.2.
* 16.0 SpringBoard (20A8372): the only education call (block of `SBFluidSwitcherViewController initWithSwitcherController:...`, 0x1c5fbc654, userInfo made by `dictionaryWithObjects:forKeys:count:1` at 0x1c5fbc750) sends exactly ONE key, EducationType = 0, for the Stage Manager alert; the old external display observer (0x1c6331f08) presents nothing (it only sets `mirroringEnabled = YES` on the first connect). The constant `SBEducationRemoteViewControllerHasPointerAndKeyboardConnectedKey` exists in 16.0 SpringBoard's data (0x1d7ba7248) but nothing in 16.0 SpringBoard references it: the shared key header already had it, which suggests, but does not prove, that the 16.0 app already contains the external display view controller.
* NOT available here: the 20A8372 SpringBoardEducation.app itself (it lives on the system volume, not in the dyld cache; no 16.0 IPSW of this build in the toolchain). So "does the 16.0 app know type 1" cannot be decided from this side.

### Decision: decide ON THE DEVICE, from the installed app

## 12. P5 step 2: hold-flip guard (Group4Focus.x `_pointerMovedInScene:`, switch `p5_holdflip`, default on) : DEVIATION from 16.2, DEVICE-UNPROVEN

**Evidence (S/u6/3 `Backport162.log`, the step 1 probe).** With a button held (touch down scene set) the logged flips alternate strictly: the press scene's own event, location INSIDE its window (for example monitor scene, (1019, 1435) in 2560 x 1440), then the other scene's event with `press scene != event scene` and the location OUTSIDE that window's bounds (iPad scene, (839, 336) in 834 x 1194, always just past the right edge), every 3 to 15 ms, phase 1 (moved). Flips before the press (touch down scene 0x0, phase 6, hover) are all INSIDE and are real crossings. The same pattern appears in log.1 for both directions (iPad press: iPad event inside, monitor event outside at (1727, 1533) in 2560 x 1440).

**Cause.** The scene of an event is taken from its HID context id (16.2 `_windowSceneForEvent:` 0x1c795df4c, ported literally); while the button is held the route is pinned to the press scene (X9Pin `pinbuttondown`), so the second copy of each move carries the other display's context with a location in the press window's coordinates mapped into the other window's space, outside it. 16.2 `_pointerMovedInScene:` (0x1c795e838) stores the scene unconditionally (checked: no touch down test in it, in `_handleActiveDisplayQualifyingEventInWindowScene:source:` 0x1c795e014 or in the sniffer 0x1c795f0d4), so the flipping is a consequence of our pin route, and the guard is a documented deviation.

**Change.** In `_pointerMovedInScene:` before the scene is stored: if a touch down scene is set and the move's touch has a view window and `!CGRectContainsPoint(window.bounds, [touch locationInView:view])`, the move is ignored entirely (the active pointer scene, the pointer observers and the active display source `pointer` are not updated). Location test, not scene equality: the first real crossing (the other scene's event inside its own window) still switches. The step 1 probe lines stay (they log the flips that are still taken).

**Log signature.** New line, first 12 per press: `coordinator: hold-flip guard N/12: pointer move for window scene <ws> ignored while a button is held (touch down scene <press>), location (x, y) is outside its window bounds (W x H)`. Expected: during one held drag no strict alternation of `updating active pointer display from A to B` / `from B to A` lines; at most one such line per real crossing (the probe `flip probe n/12` lines after a press should not alternate any more).

## 13. iPad shows a rotated on-screen keyboard while typing on the monitor (G3B.x hosted keyboard window, switch `kbhosthere`, default on) : FIX, DEVICE-UNPROVEN

**Report.** On the iPad home screen a keyboard appeared by itself, drawn rotated by 90 degrees in a tall strip on the right half of the landscape screen (screenshot images/27.webp). Log S/u10/c: `hosted keyboard window 0x121b5b280` (the iPad's) SHOWING at 16:24:01.805, HIDING / SHOWING 47 ms apart at 16:24:06, and at 16:24:31.797 the monitor's window (0x124dd6b00) SHOWING for Filza followed 53 ms later by the iPad's HIDING, HIDING, SHOWING, SHOWING. Each time the pointer or the active display had just moved to the iPad while the focused app was on the monitor.

**Root cause (decoded).** `BPMedusaHostedKeyboardWindowController -updateMedusaHostedKeyboardWindowForScene:isForeground:` (16.2 0x1c76275f4, ported literally) lets a controller act only when the keyboard scene's display (`sb_displayIdentityForSceneManagers`, which for the keyboard scene falls back to the scene's own displayIdentity, 16.0 0x1c60ee5bc) equals the controller's display. For the host scene it then asks the scene manager of THIS display. A host that lives on the other display has no handle there, so the first branch (foreground host app that cannot present the keyboard) is false, the second (SpringBoard hosts) is false, and the third decides by `chamois && host.enhancedWindowingEnabled && app.supportsChamoisSceneResizing`: true for a resizable app in Stage Manager on the monitor, so `forMedusa = YES` and the iPad's window shows the keyboard scene that the keyboard process laid out for the monitor host (host orientation / frame), unrotated by the iPad window: the 90 degree strip. In 16.2 the keyboard scene's display follows the host's display, so the two never disagree; on 16.0 UIKit they do (the scene display flips with the arbiter, the host token stays), which is also why the windows flapped. The path was confirmed from the log (the monitor's window shows with the same host, the iPad's decides on the display flip).

**Fix.** The third branch refuses when the host scene's own display (`[[host settings] sb_displayIdentityForSceneManagers]`, set by `-[SBDeviceApplicationSceneHandle _modifyApplicationSceneSettings:...]` for every app scene, 16.0 0x1c5e2bbc0) is known and differs from the controller's display: `forMedusa = NO`, `resFg = NO`. 16.2 has no such test (documented deviation). Switch `kbhosthere` (default on); with `Backport162.off.kbhosthere` the old decision returns.

**Decisive debug line at every SHOW / HIDE.** `hosted keyboard window <window scene> SHOWING|HIDING (changed|unchanged): requested by <main display scene manager _updateMedusaHostedKeyboardWindow | ...ForScene: | fan-out ... | external display scene manager ...>; reason: <foreground host app that cannot present the keyboard itself | preferred host is SpringBoard | chamois resizable host window | host can host the keyboard itself | the host scene is on another display (resizable branch refused) | picture in picture requires the Medusa keyboard | no host scene>; window scene display D orientation N; keyboard scene display D' orientation N frame (...); host <ptr bundle-scene id> on display D''; window frame (...)`. Expected after the fix: while the focused app is on the monitor the iPad window logs HIDING with reason `the host scene is on another display` and never SHOWING.

**Rotation.** Not a separate defect: it is the keyboard scene configured for the monitor host being presented in the iPad's window (the Medusa window only embeds the scene presentation view, `_SBHostedKeyboardViewController` does not autorotate, 16.0 0x1c60ff250). Showing the keyboard only on the display of its host removes the case; a keyboard on the monitor window in an orientation different from the monitor's would need the orientation agent's work (Z2Orient*), not touched here.

**Test in plain words.** Debug on. With the monitor connected, open a resizable app (for example Filza or Notes) on the monitor and type or hover there, then move the pointer to the iPad and back several times (the iPad shows its home screen). No keyboard may appear on the iPad. In `Backport162.log` the iPad window (its pointer is the one in `window scene display` = the builtin) logs HIDING with the host-on-another-display reason; the monitor window may log SHOWING for its own app. A/B: `Backport162.off.kbhosthere` brings the old behaviour back.

**Unproven.** That the keyboard scene display is the iPad at those moments (the log shows it indirectly by the iPad controller acting); the exact keyboard-scene orientation values (they are logged now). If the keyboard still shows on the iPad with host on the iPad itself (a real iPad app), that is the 16.2 behaviour.
